title: Privacy

`@lunora/privacy` handles a user's data-subject requests: an export of everything the app holds about them, an erasure of it, and the retention periods the law requires you to keep certain records for.

:::caution[Not reviewed by a lawyer]
The legal and tax values are **not** checked by a lawyer or tax adviser. Every one is marked as pending review, and the research behind them is on the [legal basis page](/docs/packages/privacy/legal). Do not rely on a default until a qualified lawyer and a tax adviser have reviewed it against your own processing.
:::

> **Experimental.** The package is under development and is not released.

## Integrate it

Declare each module's personal data as a dataset, next to the tables it describes.

```ts
// lunora/tasks/privacy.ts
import { defineDataset } from "@lunora/privacy";

export const tasksData = defineDataset("tasks", {
    legalBasis: "contract",
    origin: "provided",
    purpose: "Tasks and goals the user schedules",
    tables: {
        goals: {},
        tasks: { omit: ["activeCycle"] },
    },
});
```

Then bind the datasets, the presets and the ports into one object. The app supplies the data, storage and request ports, and the clock. The storage port must key a request's files under `<requestId>/`, and lists and deletes them as well as writing them.

```ts
// lunora/privacy.ts
import { definePrivacy } from "@lunora/privacy";
import { eu } from "@lunora/privacy/eu";
import { germany } from "@lunora/privacy/de";

import { tasksData } from "./tasks/privacy";

// The settings are fixed; the ports depend on the call, because `ctx.db` exists only inside one.
export const privacyFor = definePrivacy({
    datasets: [tasksData],
    presets: [eu(), germany()],
    // Tables that hold a user's data but are not exported, each with the reason a reviewer reads.
    exclude: { featureFlags: "Operator configuration; contains no personal data" },
    // Derives the tombstone keys. Required once the ports pass `tombstones`; keep it in a secret binding.
    tombstoneSecret: process.env.PRIVACY_TOMBSTONE_SECRET,
    ports: (ctx) => ({
        // Your ports: the data, the files, the request store, and the clock.
        data: dataPortOver(ctx),
        files: filePortOver(ctx),
        store: requestStoreOver(ctx),
        now: () => new Date(),
        newId: () => crypto.randomUUID(),
    }),
});
```

Call it from a mutation with that mutation's context: `await privacyFor(ctx).requestExport()`. The subject comes from the context's authenticated identity (the `identity` port), never from an argument, so a caller cannot act on another subject's data.

Register the durable handlers with `defineWorkflow`. The config must be an object literal in your `workflows.ts`, because codegen reads it statically. Each handler binds the ports from its own context, since a workflow step has no `ctx.db`: it reaches the data through `ctx.run`.

:::caution[Not yet verified]
Codegen has been checked only with a handler that is a property of a module-level object. The handlers here sit on the per-call `privacyFor(ctx)` result, which codegen has not been checked against yet. Plan §4.2 tracks this. Do not ship the registration on the strength of this page alone.
:::

```ts
// lunora/privacy.ts (add next to privacyFor)
export const privacyWorkflows = {
    erasureHandler: async (context: WorkflowRunContext<{ requestId: string }>) => privacyFor(context).workflows.erasureHandler(context),
    exportHandler: async (context: WorkflowRunContext<{ requestId: string }>) => privacyFor(context).workflows.exportHandler(context),
};

// lunora/workflows.ts
import { defineWorkflow } from "@lunora/workflow";

import { privacyWorkflows } from "./privacy";

export const privacyExport = defineWorkflow<{ requestId: string }>({
    handler: privacyWorkflows.exportHandler,
    limits: { steps: 25_000 },
    name: "privacy-export",
});
export const privacyErasure = defineWorkflow<{ requestId: string }>({
    handler: privacyWorkflows.erasureHandler,
    limits: { steps: 25_000 },
    name: "privacy-erasure",
});
```

A mutation opens the request with `privacyFor(ctx).requestExport(...)` and then starts the workflow with `ctx.workflows.get("privacyExport").create(...)`. The worked example is `examples/privacy`.

## What it does

- **Export (Art. 15 and 20).** Every dataset is collected, then written to a ZIP with a manifest and a readable PDF copy. The manifest says which article each dataset falls under. The download link lasts fifteen minutes, and the export expires after seven days. Run `admin.sweep()` from a cron: it deletes each expired export's files and marks the request `expired`.
- **Erasure (Art. 17).** A request enters a 14-day grace window, during which the subject can cancel. Erasure then runs one dataset at a time and deletes the subject's stored files: every file their requests wrote, and everything under each dataset's `files.prefix(subjectId)`. The request completes only after a verify step finds every table empty and every files prefix listing nothing, apart from rows a retention rule still keeps.
- **Retention.** The package decides and the app writes. `eraseBatch` receives a `disposition(dataset, table, row, now)` function bound to the presets' rules. Delete a `delete` row, anonymise an `anonymise` row, and move a `keep` row into your archive table so the next batch does not select it again. A dataset with a retained table is marked `restricted` in the export manifest.
- **Deadlines (Art. 12(3)).** The response is due one calendar month after receipt. `tick` lists requests within seven days of their deadline and those already overdue, so an operator sees a missed one.
- **Restores.** A completed erasure records a tombstone keyed by an HMAC of the subject id under `tombstoneSecret`. An erasure or a restore refuses to run without the secret once tombstones are configured. If a backup taken before the erasure is restored, `restore` erases those subjects again.

## Coverage

A table with a `userId` column must be covered by a dataset, or excluded with a reason, once the app uses `definePrivacy`. Otherwise the build fails with `privacy_table_unclassified`, which names the table.
