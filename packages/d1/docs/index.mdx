`@lunora/d1` is the D1-backed storage adapter for tables marked
`.global()`. It wraps the Workers `D1Database` binding with the Sessions
API (so read-your-writes works across replicas) and ships a migration
runner the CLI's `migrate` command relies on.

```ts
import { D1Client } from "@lunora/d1";

const client = new D1Client(env.D1, { bookmark: bookmarkFromRequest });
const { results } = await client.query("SELECT * FROM users WHERE id = ?", [userId]);
```

## `D1Client`

The main façade. Maintains a `D1Session` per request, threads the
`x-d1-bookmark` header through, and exposes typed `query` / `run` / `batch`
methods.

```ts
const client = new D1Client(env.D1);
const bookmark = await client.run("INSERT INTO users (...) VALUES (?, ?)", [a, b]);
```

## `D1Session`

Lower-level handle when you need to batch multiple statements under a
single bookmark. Mirrors the `D1DatabaseSession` interface from
`@cloudflare/workers-types`.

## `D1DatabaseLike` / `D1PreparedStatementLike` / `D1SessionLike`

Structural type aliases. Useful in tests when you want to swap in a mock
without depending on the full Workers types package.

## `MigrationRunner`

Applies a sequence of `Migration` records against a D1 database. Tracks
applied versions in the `_lunora_migrations` table.

```ts
import { MigrationRunner } from "@lunora/d1";

const runner = new MigrationRunner(env.D1, [{ version: 1, name: "init", sql: readFileSync("migrations/001_init.sql", "utf8") }]);

const { applied, skipped } = await runner.run();
```

`MigrationRunnerResult.applied` is the versions that were just applied,
`skipped` is what was already on disk. Use `lunora migrate generate` to
**produce** the SQL — `MigrationRunner` is what actually **applies** it at
deploy time.

## `Migration`

```ts
interface Migration {
    version: number; // monotonic integer
    name: string; // human label (used in logs)
    sql: string; // raw SQL — keep one statement per file
}
```

## Atomicity

When `db.batch()` is available (it is for every D1 binding shipped by
Wrangler ≥ 3.30), each migration runs atomically together with its
tracking-table INSERT. Otherwise the runner emits a console warning and
falls back to sequential execution — a crash mid-migration may leave the
tracking table out of sync.
