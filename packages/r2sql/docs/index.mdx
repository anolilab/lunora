`@lunora/r2sql` queries Cloudflare [R2 SQL](https://developers.cloudflare.com/r2-sql/) — the serverless, distributed query engine over [Apache Iceberg](https://iceberg.apache.org/) tables in [R2 Data Catalog](https://developers.cloudflare.com/r2/data-catalog/) — from a Lunora **action** via `ctx.r2sql`, with a typed, chainable query builder.

It gives first-class DX to the [2026-06-21 R2 SQL release](https://developers.cloudflare.com/changelog/post/2026-06-21-window-functions-distinct-set-operations/): **window functions**, **`DISTINCT` / `DISTINCT ON`**, **`QUALIFY`**, and **set operations** (`UNION` / `INTERSECT` / `EXCEPT`).

```sh
pnpm add @lunora/r2sql
```

## Action-only and non-reactive

R2 SQL has **no Workers binding** — every query is an HTTPS round-trip to Cloudflare's REST endpoint. So, exactly like Hyperdrive's `ctx.sql`, it is non-deterministic external I/O:

- `ctx.r2sql` is typed onto **`ActionCtx` only** — using it in a `query`/`mutation` is flagged by the `r2sql_outside_action` advisor lint.
- Its reads are **not** tracked by Lunora live queries; a subscription will not re-run when an Iceberg table changes. To surface analytics reactively, read in an action and project the result into a `defineSchema` table.

This positions R2 SQL where it belongs: large-scale analytical reads over your data lake, not the operational read path Lunora's Durable Objects own. (Unlike Convex, which only offers streaming **export** to external warehouses, the engine is queryable in-platform; the model is closer to Supabase Analytics Buckets, but reached from a Lunora action rather than a Postgres FDW.)

## Setup

Create a Cloudflare API token scoped to **R2 SQL (read)**, **R2 Data Catalog**, and **R2 storage**, then provide it (plus account id and bucket) from your environment. The token is a secret — keep it in `.dev.vars` / Worker secrets, never a binding:

```ini
# .dev.vars
R2_SQL_TOKEN=...
R2_SQL_ACCOUNT_ID=...
R2_SQL_BUCKET=analytics
```

Codegen wires `ctx.r2sql` when an action imports `@lunora/r2sql` or reads `ctx.r2sql`. By default the client is built from `R2_SQL_TOKEN` + `R2_SQL_ACCOUNT_ID` (or `CLOUDFLARE_ACCOUNT_ID`) + `R2_SQL_BUCKET`; for full control, pass an `r2sql` config thunk to `createShardDO()`:

```ts
createShardDO({
    r2sql: (env) => createR2Sql({ accountId: env.CLOUDFLARE_ACCOUNT_ID, apiToken: env.R2_SQL_TOKEN, bucket: "analytics" }),
});
```

## Usage

```ts
import { action } from "@/lunora/_generated/server";
import { desc, fn, sql } from "@lunora/r2sql";

// Top 3 customers by amount in each region — a window function + QUALIFY.
export const topPerRegion = action({
    args: {},
    handler: async (ctx) => {
        const { rows } = await ctx.r2sql
            .from<{ customer_id: string; region: string; total_amount: number }>("sales.orders")
            .select("customer_id", "region", "total_amount")
            .qualify(
                fn
                    .rowNumber()
                    .over({ partitionBy: "region", orderBy: desc("total_amount") })
                    .lte(3),
            )
            .run();

        return rows;
    },
});
```

### DISTINCT / DISTINCT ON

```ts
ctx.r2sql.from("sales.orders").select("region", "department").distinct();

ctx.r2sql.from("sales.orders").distinctOn("region").select("region", "customer_id", "total_amount").orderBy("region", desc("total_amount"));
```

### Window functions

```ts
ctx.r2sql.from("sales.orders").select(
    "customer_id",
    fn
        .rowNumber()
        .over({ partitionBy: "region", orderBy: desc("total_amount") })
        .as("rank_in_region"),
    fn
        .lag("total_amount")
        .over({ partitionBy: "region", orderBy: desc("total_amount") })
        .as("prev_amount"),
    fn.sum("total_amount").over({ orderBy: "total_amount", frame: "ROWS BETWEEN 2 PRECEDING AND CURRENT ROW" }).as("running_total"),
);
```

### Set operations

```ts
const blocked = ctx.r2sql
    .from("security.firewall_events")
    .select("zone_id")
    .where(sql`action = ${"block"}`);
const enterprise = ctx.r2sql
    .from("security.zones")
    .select("zone_id")
    .where(sql`plan = ${"enterprise"}`);

// Enterprise zones with no firewall events.
const { rows } = await enterprise.except(blocked).run();
```

### Safe values

R2 SQL has no parameter binding, so values are inlined into the statement. Always bind user input with the `sql` tag (or `lit()`), which escapes every interpolation:

```ts
ctx.r2sql
    .from("sales.orders")
    .where(sql`region = ${untrusted}`)
    .limit(100);
```

## Raw queries and schema discovery

```ts
const { rows } = await ctx.r2sql.query<{ total: number }>(sql`SELECT COUNT(*) AS total FROM sales.orders`);

await ctx.r2sql.explain(sql`SELECT * FROM sales.orders LIMIT 10`, { format: "json" });

await ctx.r2sql.showDatabases(); // namespaces
await ctx.r2sql.showTables("sales"); // tables in a namespace
await ctx.r2sql.describe("sales.orders"); // columns + Iceberg types
```

## Limits

R2 SQL is read-only (`SELECT`); writes go through Pipelines / PyIceberg. `LIMIT` caps at 10,000 (default 500). See the [SQL reference](https://developers.cloudflare.com/r2-sql/sql-reference/) for the full supported grammar.
