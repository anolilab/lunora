`@lunora/platform-node` is the Node **host**: the `@lunora/platform` contracts —
`ShardHost`, `SocketHost`, `ShardDirectory`, `ShardKvStore`, `SchedulerHost` —
implemented over `better-sqlite3` and an in-process registry, plus `.global()`
tables over `@lunora/sql-store`, workflows over `@visulima/workflow`, and object
storage on the local filesystem.

```ts
import { createNodePlatform } from "@lunora/platform-node";

const platform = createNodePlatform({ path: "./shard.sqlite3" });
```

## Status

**Experimental, and not a shipping target.** There is no `lunora dev --target
node` — this package ships no dev server. A `@lunora/config` deploy driver
(`node`) does exist, but `provision` is a reporting step, not a writing one: it
tells you, once, which declared features this target cannot serve, and it has
no toolchain to shell out to (no `wrangler`-equivalent), because there is
nothing remote to deploy to, tail logs from, or store secrets in.

Its API snapshot is gated at the **experimental** tier
(`scripts/api-snapshot.js`): here is a public-API change and must be reviewed
as one. This package is Experimental — the snapshot records how its surface
moves, and carries **no SemVer promise until the package graduates**
(`ROADMAP.md`'s [graduation bar](https://github.com/anolilab/lunora/blob/alpha/ROADMAP.md#experimental--stable-the-graduation-bar)).
`scripts/check-roadmap-tiers.js` fails the install if the roadmap and the
snapshot tier ever disagree.

Read the table below as an honest self-rating, not an invitation to run
production traffic on it.

the feature, and a bare Node process provides essentially none of them.
`localSql` is the exception, because SQLite genuinely is the platform primitive
there.

## What it is for today

Dev and test. It exists to run the same conformance suite
(`@lunora/platform/conformance`, `@lunora/shard-engine/conformance`) against a
second host so portability is a construction check rather than a claim, and it
is a useful in-process double for exercising app code without Cloudflare
credentials. It is not wired into `lunora dev`, is not a deploy target, and the
capabilities above — one process, no distributed placement or failover, no
Cloudflare product bindings — mean it is not a substitute for the Cloudflare
host in anything that needs them.

## Known divergences

**`node-kv-store`'s serializer is not Cloudflare's, and is not even a stable
wire format on its own.** `ShardKvStore.put`'s contract says a value must be
structured-clonable and hosts serialize it durably, without pinning a wire
format. Cloudflare's `state.storage` uses the platform's own structured-clone
implementation. This host stores values as `node:v8`'s `serialize`/`deserialize`
output — the same structured-clone algorithm V8 uses for `postMessage` and
`structuredClone` itself, so it round-trips `Date`, `Map`, `Set`, `RegExp`, and
typed arrays, genuinely closer to Cloudflare's fidelity than `JSON.stringify`
would be. But `node:v8`'s format is explicitly documented by Node as **not** a
stable cross-version wire format: a value written under one Node/V8 version is
not guaranteed to `deserialize` under another. A SQLite file carried across a
Node upgrade can fail to read back values it wrote. See
`packages/platform-node/src/node-kv-store.ts` and
[`plans/234-node-host-findings.md`](https://github.com/anolilab/lunora/blob/alpha/plans/234-node-host-findings.md).
