`@lunora/platform-node` is the Node **host**: the `@lunora/platform` contracts
(`ShardHost`, `SocketHost`, `ShardDirectory`, `ShardKvStore`, `SchedulerHost`)
implemented over `better-sqlite3` and an in-process registry, plus `.global()`
tables over `@lunora/sql-store`, workflows over `@visulima/workflow`, and object
storage on the local filesystem.

```ts
import { createNodePlatform } from "@lunora/platform-node";

const platform = createNodePlatform({ path: "./shard.sqlite3" });

// …or with the emulated tiers bound. Each is a declaration: omit it and the
// corresponding member is `undefined` rather than an empty host.
const full = createNodePlatform({
    crons: LUNORA_CRONS, // from _generated/crons.ts; the whole declared set
    // The per-shard handler: crons, scheduled jobs and fan-out reach the app through it.
    // `shardDoFor` returns the one ShardDO you keep per shard (see `liveStreams`).
    onFetch: (request, shard) => shardDoFor(shard).fetch(request),
    globalTablesPath: "./.lunora/global.sqlite3", // → platform.globalTables, its own file
    objectStorageDirectory: "./.lunora/bucket", // → platform.objectStorage
    onQueueBatch: dispatchQueueBatch, // required alongside `queues`
    path: "./shard.sqlite3",
    queues: { emails }, // → platform.queues
    workflows: { orderPipeline }, // → platform.workflows, runs in the same SQLite file
});
```

## Status

**Experimental, and not a shipping target.** There is no `lunora dev --target
node`; this package ships no dev server. A `@lunora/config` deploy driver
(`node`) does exist, but `provision` is a reporting step, not a writing one: it
tells you, once, which declared features this target cannot serve, and it has
no toolchain to shell out to (no `wrangler`-equivalent), because there is
nothing remote to deploy to, tail logs from, or store secrets in.

`lunora deploy --target node` deploys to a container build context instead:
a bundled `server.mjs` whose generated entry composes this package around the
app's worker entry (every Durable Object binding, `crons: LUNORA_CRONS`,
`createNodeSecretBindings` over the `secrets_store_secrets[]` names, and
`createNodeHyperdrive` from `DATABASE_URL`), a Dockerfile on a pinned Node LTS
image that compiles `better-sqlite3` and runs as a non-root user, and a README
listing the environment it reads. The SQLite files live under
`LUNORA_DATA_DIR` (`/data` in the image), which is the volume to mount. See
`lunora deploy` in the CLI docs.

Its API snapshot is gated at the **experimental** tier
(`scripts/api-snapshot.js`): a diff here is a public-API change and must be
reviewed as one. This package is Experimental: the snapshot records how its surface
moves, and carries **no SemVer promise until the package graduates**
(`ROADMAP.md`'s [graduation bar](https://github.com/anolilab/lunora/blob/alpha/ROADMAP.md#experimental--stable-the-graduation-bar)).
`scripts/check-roadmap-tiers.js` fails the install if the roadmap and the
snapshot tier ever disagree.

Read the table below as an honest self-rating, not an invitation to run
production traffic on it.

## What it is for today

Dev and test. It exists to run the same conformance suite
(`@lunora/platform/conformance`, `@lunora/shard-engine/conformance`) against a
second host so portability is a construction check rather than a claim, and it
is a useful in-process double for exercising app code without Cloudflare
credentials. It is not wired into `lunora dev`, deploys only as the container
`lunora deploy --target node` writes (one process, which you host), and the
capabilities above (one process, no distributed placement or failover, no
Cloudflare product bindings) mean it is not a substitute for the Cloudflare
host in anything that needs them.

## On-demand profiling

`createNodeProfileHandler({ token })` captures a CPU or heap profile of the
running process through the built-in `node:inspector` `Session`, wrapped in
promises, with no native addon and no flag at boot. It serves the result as a
gzip pprof that `go tool pprof`, Pyroscope and Speedscope read. The app mounts
the handler on a bearer-guarded `POST` route of its own choosing, and
`lunora profile --target node --url <route>` calls it. A CPU capture only sees work that runs during the window. A heap capture
reports the allocations still live when it stops. Functions V8 had already
inlined before a CPU capture began can appear under their caller rather than
under their own name.

The profiler runs one capture at a time per process, and the handler refuses an
empty token when it is created. Profiling is not a `ctx.*` surface or binding,
so it has no entry in `PlatformCapabilities`.

## Known divergences

**`node-kv-store`'s serializer is not Cloudflare's, and is not even a stable
wire format on its own.** `ShardKvStore.put`'s contract says a value must be
structured-clonable and hosts serialize it durably, without pinning a wire
format. Cloudflare's `state.storage` uses the platform's own structured-clone
implementation. This host stores values as `node:v8`'s `serialize`/`deserialize`
output, the same structured-clone algorithm V8 uses for `postMessage` and
`structuredClone` itself, so it round-trips `Date`, `Map`, `Set`, `RegExp`, and
typed arrays, genuinely closer to Cloudflare's fidelity than `JSON.stringify`
would be. But `node:v8`'s format is explicitly documented by Node as **not** a
stable cross-version wire format: a value written under one Node/V8 version is
not guaranteed to `deserialize` under another. A SQLite file carried across a
Node upgrade can fail to read back values it wrote. See
`packages/platform-node/src/node-kv-store.ts` and
[`plans/234-node-host-findings.md`](https://github.com/anolilab/lunora/blob/alpha/plans/234-node-host-findings.md).

## API

Every public export of `src/index.ts`, plus the conformance entry point.

### `createNodePlatform`

**Type:** `(options?: NodePlatformOptions<Queues, Workflows>) => NodePlatform<Queues, Workflows>`

Composes every contract this package provides over one `better-sqlite3` database
file. The `queues`, `workflows`, `objectStorage`, `globalTables` and `mail` members are
`undefined` when the matching option (`queues`, `workflows`,
`objectStorageDirectory`, `globalTablesPath`, `mail`) is omitted. Call `drain()` and then
`close()` for a graceful shutdown. After `close()`, `scheduler.schedule()` and
`shard.alarms.set()` throw.

### `NodePlatform`

**Type:** interface

The object `createNodePlatform` returns. It exposes `shard`, `kv`, `sockets`,
`scheduler`, `directory`, `dispatch`, `capabilities`, `drain`, `close` and
`[Symbol.dispose]`. `drain` also drains the registry's shards (see
`createNodeShardRegistry`), plus the optional `queues`, `workflows`, `objectStorage`,
`globalTables` and `mail` members described above. `mail` runs on its own
connection to `mail.path`, a file of its own, never the shard's.

### `NodePlatformOptions`

**Type:** `{ crons?, dispatch?, globalTablesPath?, mail?, objectStorageDirectory?, onQueueBatch?, queues?, workflows? } & NodeSchedulerHostOptions & NodeShardHostOptions & NodeShardRegistryOptions`

The options for `createNodePlatform`. The shard host reads `path`, `shardKey` and
`onAlarm`, the scheduler reads `onDispatch`, and the shard registry reads
`directory`, `onAlarm` and `onFetch`. `queues` requires `onQueueBatch`, which the
platform calls for each assembled batch. `mail` takes the
[`createNodeMailHost`](#createnodemailhost) options plus a `path`, the database
file the mail host keeps its queue, sent ledger and key records in (the
`NodePlatformMailOptions` type). The file is its own, never the shard's, and
there is no default. `shard.transaction()` holds the shard's file across awaits,
so mail written on it during a mutation would be rolled back with it, and the
ack and sent record lost would mail the message again. Construction throws when
`mail.path` is not durable (`:memory:`, or the empty string, which better-sqlite3
opens as a temporary file), or is a `file:` URI asking for memory (better-sqlite3
does not read URIs, and would create a file by that literal name instead), or
names the shard's file, the `globalTablesPath` file, or a `.sqlite3`
file inside the registry `directory` (which would be opened as a shard). Paths
are compared after `path.resolve` and `realpath`, and existing files by device and
inode, so a hard link to one of those files is refused too. SQLite names its WAL
after the path, so two names for one database would each keep a WAL of their own.

Run exactly one process with `crons`: it owns the declared set. Processes do
not notify each other when a row changes, so a server only sees another
process's edit when its own timer next fires and re-reads the row. A job moved
to a more frequent schedule misses the ticks before then.

`crons` takes the generated `LUNORA_CRONS` map and is the app's whole declared
cron set: each job is armed on the scheduler and delivered through `onDispatch`
(or, with `onFetch`, straight to the shard), and a job an earlier run declared
that is missing from the map is deleted. Only a process that passes `crons`
manages that set: one that omits it, such as an admin script opening the same
file, neither fires nor deletes declared jobs. A running server whose declared
job another process removed logs a warning and stops firing it. Crons registered
through `scheduler.cron()` are re-armed either way. A failed tick is logged with
its job, error and next run time, and the schedule carries on.
Schedules are read as UTC, as Cloudflare's are, and a run that outlasts the
interval skips the ticks it covers instead of overlapping itself. Construction
throws for a job that targets a workflow (nothing on this host starts a workflow
instance from a tick), for two jobs with the same name, for a schedule with no
next occurrence (`0 0 31 4,6,9,11 *`), and for a non-empty map
when neither `onFetch` nor `onDispatch` is given.

**Type:** `(database: Database.Database) => SqlCtxExec`

Builds the SQL executor over a `better-sqlite3` connection. Its `transaction`

### `DrainOptions`, `DrainResult`, `DrainTimer`, `DEFAULT_DRAIN_TIMEOUT_MS`

**Type:** interfaces and a constant

What every `drain()` in this package takes and returns. `timeoutMs` bounds the
drain (`DEFAULT_DRAIN_TIMEOUT_MS`, 30 s, when omitted; a value that is not a
whole number from 0 to 2147483647 ms throws a `RangeError`, since Node would run
a longer timer after 1 ms), and `timer` replaces the
clock it runs on, so a test can fire the deadline by hand. The default timer is
referenced while the drain runs: a drain waiting on a promise with no I/O behind
it (a stalled shard `waitUntil`) keeps the process alive until the deadline
fires, instead of letting it exit silently. `NodePlatform.drain()` runs its host
and registry drains under that one deadline, repeating until both are idle at the
same instant, since host work can start shard work after the registry drained.
Scheduler deliveries count as busy work too: a scheduled job or cron tick
running through `onDispatch` (yours or the built-in one) is waited for until the
scheduler has recorded its outcome, and named if the deadline passes first. A `DrainResult`
reports `timedOut`, the `pending` work still running when the deadline passed,
and the work that `failed` while the drain waited (an alarm retry that could not
be written), one readable label each. Each failure is also logged with its cause
when it happens, and drains wait with settled semantics, so one failure never
stops them waiting for the rest.

### `createNodeHttpServer`

**Type:** `(options: NodeHttpServerOptions) => Promise<NodeHttpServer>`

Serves an app worker's `fetch` over `node:http` and resolves once the server is
listening. `fetch` is required. `host` defaults to the loopback interface. A
handler that throws is answered with 500 and logged with its error, its method
and its path (never the query string, which can carry a token). `drain()` stops
the listener, then waits until every response that was in progress when it
began is written or its client is gone; a request still arriving on an open
connection is answered with `Connection: close` and not waited for. Event
streams and WebSockets are not waited for, and `close()` ends them. It is
bounded by a deadline (see `DrainOptions`, checked before anything is stopped, so an invalid one leaves the server serving) and resolves with what was still
unfinished, which it also logs. A graceful shutdown refuses new requests in its
`fetch`, awaits `drain()`, then `close()`.

### `createNodeHyperdrive`

**Type:** `(url?: string) => NodeHyperdriveBinding`

Builds the `HYPERDRIVE` binding from a `postgres://`, `postgresql://`,
`mysql://` or `mariadb://` URL, `process.env.DATABASE_URL` unless given. A
Postgres URL may name a Unix socket the libpq way, `postgres:///db?host=/var/run/postgresql`,
and the socket directory becomes `host`. Without a port in the authority, a
Postgres `?port=` (1 to 65535) sets `port`; the authority's port wins when both are set. A URL with any TLS option other than an
explicit off (`sslmode=prefer` or `require`, `ssl=true`, `sslrootcert=…`) keeps it
only in `connectionString`; the binding's discrete fields throw instead of letting
a driver built from them connect without TLS, so build the driver from
`connectionString`. `sslmode=disable` and `ssl=false` keep the discrete fields. Put it on the `env`
under the binding name the app reads, and the app's `.hyperdrive((env) => …)`
wiring builds `ctx.sql` from it unchanged. There is no pool or query cache in
front of the database: the driver connects to it directly.

### `createNodeMailHost`

**Type:** `(database: Database.Database, options?: NodeMailHostOptions) => NodeMailHost`

Give it a connection nothing else opens a transaction on, ideally a file of its
own, as `createNodePlatform({ mail: { path } })` does. On a shard host's
connection, a poll during `shard.transaction()` writes inside it, and that
transaction's rollback would undo the acks and sent records and resend.

Queues and delivers `@lunora/mail` sends. It declares a `lunora-mail` queue on
`createNodeQueueHost` and returns `{ queue, mailer, poll, drain, deadLetters }`.
`mailer.queue()` writes a durable row, and so does a mailer you build in your own
module with `createMailerFromEnv(env, { queue })`. `queue.send(body, { delaySeconds })`
holds a send back. `delaySeconds` must be a whole number from 0 to 86,400 (24
hours), as on Cloudflare Queues. Any other value, or any other option, throws
rather than being clamped or dropped. Each `poll()` sends at most one
batch of up to 10 due rows through `consumeQueuedSend`, so drain a backlog with
further polls. The `transport` option, such as an SMTP client you
wrap as a `MailTransport`, wins over `RESEND_API_KEY`, which is read only without
one. Capture follows `createMailerFromEnv`'s rule, the same one Cloudflare applies:
`LUNORA_MAIL_CAPTURE=1` forces it and `=0` forces delivery. Unset, mail is captured
when every set value of `CF_ENV`, `ENVIRONMENT`, `NODE_ENV` and `WORKER_ENV` names
a dev environment (`dev`, `development`, `local`, `localhost` or `test`). Node
tooling often sets `NODE_ENV=test` by itself, so construction logs one warning
whenever it captures, naming the variable that chose capture. A
`LUNORA_MAIL_CAPTURE` value other than `1`, `true`, `0` or `false` is ignored by the
rule, and the warning says so instead of blaming it. To see captured mail
in the studio, put a `SHARD` namespace and `LUNORA_ADMIN_TOKEN` on `env`. Without
them, captured mail is discarded, and the warning says so.

The `mail` registry starter (`lunora registry add mail`) does not run on Node: it
imports `cloudflare:workers` and `cloudflare:email`. On Node, send through
`platform.mail.mailer`, or build the mailer from your own `env` with `queue`.

Delivery is at-least-once, narrowed:

- A claimed batch (up to 10 sends, run one after another) stays hidden for about 18
  minutes. That covers every send running to its 60-second deadline, so an
  overlapping `poll()`, or a second process on the same file, never claims a send
  that is still in flight. A crash mid-batch redelivers after that lease.
- Before it sends, a delivery claims its idempotency key in
  `_lunora_mail_claims`, atomically. A second row with the same key waits 180
  seconds instead of sending alongside it, even from another process on the file.
  The claim names the row holding it, so a row redelivered after a crash takes
  its own claim back and sends. Another row's abandoned claim lapses with the
  lease.
- A key records the content it was first queued with, at enqueue, so the first
  message queued under a key owns it whatever order rows are delivered in. The
  reservation and the row insert run in one `BEGIN IMMEDIATE` transaction, after
  the body has been validated and encoded. So no process on the file ever sees a
  reservation without its row, and a failed enqueue leaves nothing behind. The
  record lives as long as the key's delivery history, 15 days from its last
  delivery: one horizon for all of a key's evidence. So a key reused with new
  content within 15 days is refused at enqueue, not accepted and then dropped as
  a late repeat. Once it lapses, the key still belongs to the oldest queued, retrying or
  parked row that carries it, judged by that row's own stored content. So
  `mailer.queue()` and `queue.send()` throw for a key with different content for as
  long as any row of the original is live. Content is compared on the fields the
  consumer sends, with a lone recipient and a one-element list counting as the
  same. A row found superseded when it is delivered (queued before any record
  existed) is logged as the error `lunora.mail.idempotency_key_conflict` and parked
  in `deadLetters`, never acked. Expired records and abandoned claims are pruned at
  most once a minute.
- A key's deliveries are numbered across every row that carries it, and that
  number, not a row's own attempt count, is what the attempt marks are keyed on.
  The dedupe window runs from the key's first delivery. A second row queued for a
  key after Resend's window is judged against the first row's attempts and refused
  when one may have landed. Row attempts still set the retry budget. The content
  record is kept at least as long as the sent record.
- `_lunora_mail_sent`, in the mail database beside the queue, records each key once the transport
  confirms the send, and keeps it for 24 hours. It also keeps the attempt marks
  `consumeQueuedSend` writes, for 15 days. A second enqueue of a sent key is acked
  without a send. A redelivery past Resend's dedupe window is refused when an
  earlier attempt may have landed. Expired rows are pruned at most once a minute,
  through an index.
- The dedupe window is measured on the host clock (`now`), the same clock the
  queue and the ledger use.
- A redelivery of a key 15 or more days after the key's first delivery is
  refused and logged as `lunora.mail.send_evidence_expired`, whatever brought it
  back. The clock runs from that first attempt, not from the enqueue: a row first
  polled long after it was queued is a fresh first attempt, and its transient
  failure is retried. A key's delivery history is kept for as long as a queued,
  retrying or parked row queued before its expiry still carries the key, and it
  resets for a row queued after it had expired. Rows queued after the expiry are
  a new use of the key, so a fresh pair of matching sends delivers one and
  dedupes the other. So a duplicate of an already-sent mail,
  left pending through a long gap, is refused rather than sent as a first send.
- A failure after the provider accepted a send (updating the key's content record,
  or releasing its claim) is logged as its own error,
  `lunora.mail.content_record_failed` or `lunora.mail.claim_release_failed`. It is
  never a refusal, never retries the send, and never stops the rest of the batch.
- A crash after the provider accepted a send, and before its key was recorded,
  still redelivers. Only a provider that dedupes on the key (Resend) drops that
  repeat.
- Sends are claimed oldest first, and a retried send goes behind newer ones.

A retryable failure is logged as a warning, with the error's `cause` chain and
stacks, and retried three times. The delivery that parks it is logged as the error
`lunora.mail.send_dead_lettered`, and `deadLetters.list()` lists it. An
outcome-unknown failure waits 180 seconds before the retry, counted from the
failure, not from the start of a slow batch. A refused or malformed
send is logged as an error and dropped, because a retry could mail a second copy.
The queue name `lunora-mail` is reserved for the mail host: `createNodeQueueHost`
refuses an app queue of that name on any connection, in this process or another,
since it would claim and drop mail rows as its own. Separately, two app hosts on
one database connection cannot declare the same queue name.
`deadLetters.requeue(id)` revives only a parked mail send and keeps its attempt
count, so a send that may already have landed is refused rather than mailed again
once Resend's window has passed. It throws for a send queued 15 or more days ago,
since its attempt record has expired. The app's `platform.queues.deadLetters.requeue`
cannot revive a mail send. `drain()` waits for every poll in flight. `createNodePlatform`'s `drain()`
calls it before and after the shard drain, so a poll started by `shard.waitUntil`
work is waited for too. `env` defaults to `process.env` and is
read once. Construction throws when `MAIL_FROM` is unset, or when neither
`transport` nor `RESEND_API_KEY` gives it a way to deliver. Cloudflare's
`send_email` binding and inbound Email Routing do not exist on Node.

### `createNodeShardRegistry`

**Type:** `(options?: NodeShardRegistryOptions) => NodeShardRegistry`

Builds the in-process shard registry. `directory` names the folder that holds one
SQLite file per shard. Omit it for in-memory shards, which do not survive a
restart. `onAlarm` and `onFetch` are the registry's delivery hooks. `drain()`
waits until every shard is idle: no `onFetch` or `onAlarm` call in flight (cron
and scheduled-job deliveries included), no `waitUntil` work pending and no socket
close handler running. Each pass re-reads every live shard, so work handed to a
shard after its own drain finished, or a shard opened while draining, is seen;
Alarm deliveries count until their retry, if any, is written, so a shutdown
cannot lose a failed alarm. A retry waiting for another task's transaction to end
always settles: it is written once the transaction ends, superseded by a later
`set` or `delete`, or, if the shard closes first, given up and logged. A retry
write that fails (contention from another process) is tried again with backoff
before the alarm is given up and logged. `idle()` answers the same question synchronously.
It returns only when a full pass finds nothing running, or when its deadline
passes, logging one line per shard with how many requests, alarms and
`waitUntil` tasks it still had (never the request or its payload). Await it before `close()`, which does not wait. `close({ force: true })`, for
after a drain has finished or reached its deadline, disposes a shard whose socket
close handler is still running instead of waiting for it, and logs it. A shard
that fails to close does not stop the others: every one is tried, each failure is
logged, and `close()` then throws one `AggregateError` naming them.
`NodePlatform.close()` runs all of its teardowns the same way.
`rearmPersistedAlarms()` (on the registry and on `NodePlatform`) opens every
stored shard that has a persisted alarm, so a restarted process fires it without
waiting for a request to that shard; call it once before taking traffic. Shards
without an alarm stay closed. `idle()` reports synchronously whether anything a
drain would wait for is running, and `drainTogether(parts, options)` drains
several registries or platforms under one deadline until all are idle in the same
pass, since work on one can start work on another after it drained.
