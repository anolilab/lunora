# @lunora/cloud — Lunora Cloud control plane

The managed-platform control plane, **dogfooded on Lunora itself** — the platform's own metadata store is a Lunora
app. This is the service that provisions and tracks tenant deployments on
Cloudflare Workers for Platforms; it is **not** a tenant worker.

> Status: **Phases 1–4 implemented as code**, verified by codegen, tsc, eslint,
> and unit tests; end-to-end runs need live Cloudflare and provider keys. In
> place: the data model, CRUD functions, org/deploy-key authorization, the deploy
> orchestration core (token bucket, per-cell scheduler, state machine) and the
> `POST /v1/deploy` streaming endpoint, a **real Cloudflare REST provisioner**
> (`src/cloudflare/api.ts` — D1/R2 create, dispatch-script upload, secrets), the
> dispatcher Worker with **per-plan runtime limits**, the server-rendered
> hosted studio (TanStack Start — `src/routes` + `src/client`), a dev seed
> (`scripts/seed.ts`), **billing on `@lunora/payment`** (Creem — a Merchant of Record
> that handles global sales tax/VAT — checkout/portal/webhook,
> entitlements, metering ingestion), and **hardened better-auth** (mail-backed
> verification/reset, optional OAuth, 2FA/passkeys, rate limiting). Still open
> (needs live infra/services): end-to-end deploy validation, the billing-provider
> charge wiring against a real Creem account, cell bring-up IaC, custom domains,
> and the items still marked infrastructure-blocked in [`GAPS.md`](./GAPS.md).

### Topology (provisional — a real decision flagged in the plan)

All control-plane tables are `.global()` (D1-backed): the plan's "Worker + D1"
control plane, with relational, cross-queried, low-volume metadata. Reads use the
per-table `findMany({ where })` facade. (Per-tenant _sharding_ in the plan refers
to the tenant apps' own ShardDOs, not the control plane's own bookkeeping.)

### Authorization (`lunora/authz.ts`)

Two paths gate every org-scoped function:

- **User session** → `assertMember(ctx, orgId, roles?)` — dashboard callers must
  be members; closes the IDOR hole where any signed-in user could touch any org.
- **Deploy key** → `authorizeDeployKey(ctx, orgId, key, projectId?)` — CI/deploy
  callers have no session; a valid, unrevoked, org-matching key is the credential.

### The deploy API (`POST /v1/deploy`)

Mounted as the worker's `httpRouter` (lowest-priority matcher). Flow: read the
`Authorization: Bearer <deployKey>`, `deploy_keys:verify` it, `deployments:create`
a queued record, then drive `runDeployment` while streaming **NDJSON progress**
(`accepted` → `queued` → `provisioning` → `live`/`failed` → `done`), patching
status via `deployments:updateStatus` per phase. All Cloudflare work is paced by
the per-cell `CellScheduler`. The route reaches these mutations through the Lunora
action context (`env.__lunoraCtx.runMutation`); they stay **public** (not
`internalMutation`) because that dispatch carries no system flag — an internal
function would 404 at the RPC visibility gate — so authorization is enforced
inside each mutation (deploy key or membership).

### The provisioning seam (`src/provision.ts`)

By design, the control plane's only coupling to the deploy
substrate lives behind the `Provisioner` interface. The shipped implementation
(`createCloudflareProvisioner`) talks to Cloudflare through the injected
`CloudflareApi` port (`src/cloudflare/api.ts`) over the **documented REST API**:
`deploy` provisions per-tenant D1/R2, uploads the user Worker into the dispatch
namespace with binding + DO-migration metadata, applies secrets, and returns the
content hash + routed URL; `destroy` removes the script. The port boundary keeps
orchestration unit-testable with a fake, and means an `alchemy@next`-backed
implementation could replace `createHttpCloudflareApi` later with no change above
this module. (What still needs a live account is end-to-end validation against
real Cloudflare — the wire calls themselves are implemented, not stubbed.)

### Billing & metering (`lunora/billing.ts`, `src/billing/`, §4)

Billing rides `@lunora/payment` with the **organization id as the payment
`referenceId`**. `src/server.ts` wires the Creem adapter into `createShardDO({
payment })`, so the billing functions get `ctx.payments`: `checkout` / `portal`
(owner/admin actions that redirect to Creem's hosted pages), `entitlements` / `subscription`
(member reads that resolve plan → features/limits through `LUNORA_CLOUD_PLANS`,
falling back to the free baseline), and `processWebhook` (signature-verified,
mounted at `POST /v1/billing/webhook`). Entitlement reads work without Creem
keys; only live calls need them.

**Quota is enforced against live subscription state**, not the static
`organizations.plan` column: `lunora/entitlements.ts` resolves the org's
entitlements from its synced `subscriptions` (the single source of truth), and
`projects`/`members` creation call `assertWithinQuota` — so a plan upgrade
raises the limits immediately, with no column to keep in sync.

Platform **metering** is end-to-end: the dispatcher emits one Analytics Engine
data point per tenant request (`src/metering/analytics.ts`, the source) and
applies **per-plan runtime limits** (`limitsForPlan` → `env.DISPATCHER.get`,
resolved via the cached `GET /v1/tenants/plan` lookup). Events also land in the
`platformUsage` ledger via `usage.ingest` (`POST /v1/usage`, deploy-key auth);
an hourly `usage.rollup` cron compacts closed periods, and `usage.summary` reads
the total. The AE→ledger reader (`createHttpAnalyticsReader`) is the prod rollup
seam (runs at the edge with the account token).

### Tenant secrets (`lunora/secrets.ts`, `src/secrets/crypto.ts`, §7)

Tenant env secrets are **AES-256-GCM encrypted at the edge** before storage:
`POST /v1/secrets` encrypts with the `SECRET_ENCRYPTION_KEY` master key, so the
control-plane D1 only ever holds ciphertext + a per-secret IV. `list` returns
names only; at deploy time the handler fetches `listEncrypted` and decrypts the
values into the tenant Worker's script secrets (alongside the platform-owned
`LUNORA_ADMIN_TOKEN`). The plaintext never reaches a browser.

### Auth (`src/server.ts`, §3)

The hosted studio runs on hardened better-auth (`@lunora/auth`): email/password
with **mail-backed verification + password reset** (`@lunora/mail`, captured into
the studio Mail tab in dev), optional GitHub/Google OAuth (enabled only when the
env creds are present), the `admin` / `inviteOnly` / `twoFactor` / `passkey`
plugins, and better-auth's built-in request rate limiting. The `/v1/*`
control-plane surface adds a per-IP `@lunora/ratelimit` cap. Org membership stays
the Lunora `organizations`/`members` model — the better-auth `organization`
plugin is deliberately omitted to avoid two parallel org models.

#### Registration is invite-only

`inviteOnly()` (`@lunora/auth/plugins`) makes account creation a **platform**
decision: no user row is written for an address with no unspent invitation,
whatever minted it — `/sign-up/email`, an OAuth callback, or
`AuthAdmin.createUser`. It declares the `signUpInvitation` table, so
`ensureMigrated` provisions it with nothing further to write.

Operators issue invitations from the studio's auth dashboard — installing the
plugin is what lights that path up end to end: `createAuthAdmin` grows
`create` / `list` / `revokeSignUpInvitation`, the runtime exposes them as admin
routes, and `@lunora/studio` renders its sign-up-invitations panel off
`capabilities.inviteOnly`. The invitation link is
`/login?email=<address>&invite=<token>`; the token is returned in the clear
exactly once, and only its SHA-256 is stored. The sign-up form reads `?invite=`
off the URL and submits it as `inviteToken`.

Team invitations bridge into it. `POST /v1/invitations/send` mints a **sign-up**
invitation alongside the org invitation whenever the invited address has no
account, and mails both links — sign-up first, because accepting needs a session
and a stranger has none. The bridge is scoped: the org invite is already gated on
`assertMember(owner|admin)` and rate-limited, and the sign-up invitation is
issued for exactly the address it names, so an org admin can admit someone to the
cell only by inviting them to their own org, one address at a time. An address
that already has an account gets no sign-up link — a second invitation would be a
second account, not a faster route into the org.

Arriving on `?invite=` opens `/login` on the sign-up form rather than sign-in.
The route derives that from `validateSearch`, not `location.search`, so the
server and the client agree; the token itself stays out of the rendered form and
is read at submit time.

`allowFirstUser` is on **only in dev** (`WORKER_ENV === "development"`), where
`scripts/seed.ts` signs its user up through the real endpoint against a database
that has none. In production that carve-out is a race between deploying and the
owner signing up, so seed the first invitation by hand instead
(`createSignUpInvitation`, or the studio panel from an already-bootstrapped
cell).

`emailAndPassword.requireEmailVerification` is on. An invitation is keyed by
address, and better-auth writes the user row before it mails the token — without
verification, whoever signs up holds a session immediately. The dev seed works
around it the way the studio would: it marks its own address verified through the
admin `users/update` route, under the `LUNORA_ADMIN_TOKEN` boundary, because in
dev the verification mail is captured into the Mail tab and no script can click
it.

The auth instance itself is built in `src/auth.ts`, not `src/server.ts` — the
invite route in `src/deploy/router.ts` needs it too, and `server.ts` already
imports that router, so reaching back the other way would be a cycle.

### Seeding a dev database (`scripts/seed.ts`)

A cold database is not merely empty, it is unusable: `organizations:create`
places every new organization on a **cell**, and with no cell in the fleet the
first thing you do after signing up fails. `pnpm run seed` fixes that, and fills
the dashboard with enough data to actually look at.

It talks HTTP to a **running dev server**, so use two terminals:

```bash
pnpm --filter "@lunora/cloud" run dev     # terminal 1
pnpm --filter "@lunora/cloud" run seed    # terminal 2
```

Then sign in at `/login` with:

|              |                     |
| ------------ | ------------------- |
| **Email**    | `dev@lunora.local`  |
| **Password** | `dev-password-1234` |

What it creates — a `dev-cell` fleet cell, the **Acme Dev** organization
(`/acme-dev`, pro plan) owned by that user, a **Web** project, a live production
deployment (`acme-dev-web`), an ingest deploy key, and telemetry: 24 log lines at
mixed levels, two 24-point hourly metric series, six trace spans, and two error
events that group into an issue. Timestamps fan out over the preceding hours so
the charts have a shape rather than one spike at "now".

Overridable via the environment: `LUNORA_SEED_URL` (default
`http://localhost:5174` — set this when Vite falls back to 5175+ because the port
was taken), `LUNORA_SEED_EMAIL`, `LUNORA_SEED_PASSWORD`. The
`LUNORA_ADMIN_TOKEN` for cell registration is resolved by `@lunora/config` — the
environment first, then `.dev.vars`.

**It refuses to run against a non-loopback host.** Everything here is destructive
against a real control plane and is authorized with whatever credentials you have:
it creates an account with a published password, sends your `LUNORA_ADMIN_TOKEN`
to the target, force-activates the project's newest deployment, and revokes any
`dev-seed` key. Set `LUNORA_SEED_ALLOW_REMOTE=1` to override, deliberately.

**Re-running is safe.** Every stage looks for what it would create first, because
none of the underlying mutations dedupe — `cells:register` inserts blindly, so an
unconditional seed would grow a fresh cell per run. Telemetry keys its check off
the seeded _logs_ rather than the deploy key: issuing a key can succeed while the
ingest behind it fails, and keying off the key would report a contented
"(exists)" forever while the views stayed empty.

Two stages report a skip instead of data, and neither is a bug in the script:

- **domain** — `domains:add` requires the `customDomains` entitlement, which
  resolves from an org's _synced subscription_ rows. Only the billing provider's
  signature-verified webhook writes those, so a local worker with no provider
  cannot honestly reach one.
- **builds** — `builds:recordPush` requires a GitHub installation the org has
  _claimed_, and installations are recorded only by the signature-verified GitHub
  webhook.

Everything is seeded **through the real surfaces** — better-auth for the user,
the `LUNORA_ADMIN_TOKEN`-gated `POST /v1/cells` for the cell, public RPC for the
rest — rather than by writing rows into D1 behind the app's back. That keeps
seeded state indistinguishable from state a user could create, and makes the
script double as a smoke test of exactly the paths a cold start depends on. It is
how several control-plane defects were found.

To start over, delete the local state and re-seed:

```bash
rm -rf apps/cloud/.wrangler/state/v3/{d1,do}
```

The hosted studio and the control-plane Worker (`src/server.ts`) are one
Cloudflare Worker on a single origin, so the studio reaches `/api/auth/*`
(better-auth) and the Lunora query/mutation endpoints with no cross-origin setup.

The studio is a **TanStack Start** app, server-rendered rather than a CSR SPA:
route loaders preload their queries on the server, and the client hydrates and
upgrades them to live subscriptions. `src/server.ts` keeps its own hand-written
entry (dispatcher routing, deploy API, admin proxy, auth, tail consumer, cron
fan-out, queue consumer) and mounts the SSR handler as the lowest-priority
`httpRouter`, so a render fault can never disturb the realtime plane.

Copy `.dev.vars.example` → `.dev.vars` and fill `LUNORA_ADMIN_TOKEN` and
`AUTH_SECRET` (the studio's better-auth session secret). Before a real deploy,
create the D1 database and replace the `database_id` placeholder in
`wrangler.jsonc`.

## Analytics (PostHog)

Two halves, both **inert without configuration** — a cell with no PostHog
project runs exactly as it did before this existed.

**The studio** (`src/client/analytics.ts`) captures manual events only.
`autocapture` is **off**: it records the text and attributes of whatever was
clicked, and on the Logs tab that is a tenant's log line, on Secrets a secret
name. Every event this app sends is written by hand, so the payload is a
decision someone made rather than whatever happened to be in the DOM.

**Session replay is on, and masks by default.** This is the part to understand
before adding a screen. The obvious configuration — `maskTextSelector` listing
the panels that hold tenant data — is an allowlist of things to _hide_, so a
panel added later is recorded until someone remembers it, and the failure is
silent and retroactive: the recording has already left the browser. Instead
every text node is masked and `data-ph-unmask` is the exception:

```tsx
// Safe to record: static chrome, no tenant data.
<CardTitle data-ph-unmask>Deployments</CardTitle>
```

A new screen therefore leaks nothing on the day it ships. Unmask navigation
chrome and static labels — enough to see which screen someone was on and which
control they reached for, which is what a replay is for. Never unmask a subtree
that renders rows from a query.

Inputs are masked wholesale (`maskAllInputs`), since a form field here is a
hostname, a secret value, or a search over tenant logs.

The signed-in operator is attached by better-auth **user id** only — no email,
no name. That id is already the subject of every audit-log row, so it adds no
linkage the control plane did not already hold. `resetOperator()` runs on
sign-out so the next person on a shared machine is not attributed to the last.

**The Worker** (`src/analytics/capture.ts`) records platform events for
self-observability (GAPS.md E1 — the studio observes tenants; nothing observed
us). Plain `fetch` rather than `posthog-node`: that SDK batches on a timer and
flushes on process exit, and a Worker isolate has neither, so a queued batch is
simply lost. One request per event, handed to `waitUntil`.

These events are about the **platform**, not about people: keyed on the
organization and the cell, carrying ids and outcomes — never script contents,
secret values, log lines or hostnames. Capture is best-effort and swallows its
errors, because a telemetry outage must not fail the deploy that triggered it.

## Deploy

A cell is **three Workers**, each with its own config, deployed together:

| Worker              | Config                      | What it is                                                    |
| ------------------- | --------------------------- | ------------------------------------------------------------- |
| `lunora-cloud`      | `wrangler.jsonc`            | The control plane + hosted studio (`src/server.ts`)           |
| `lunora-dispatcher` | `dispatcher.wrangler.jsonc` | Hostname → tenant script routing (`src/dispatcher/worker.ts`) |
| `lunora-log-tail`   | `tail.wrangler.jsonc`       | Dispatch-namespace tail consumer (`src/tail/worker.ts`)       |

### Environments

Each config declares two named environments, `staging` and `production`. The
top level of each file is the **local-dev** target — `lunora dev` and `vite dev`
read it, and CI never deploys it, because every deploy passes `--env`.

Cloudflare does not inherit resource bindings into a named environment, so each
block restates its `vars`, `d1_databases`, `r2_buckets`, `queues`,
`durable_objects`, `dispatch_namespaces`, `analytics_engine_datasets`,
`pipelines`, `ai` and `version_metadata`. A key left out of a block is a binding
the deployed Worker does not have, and that surfaces at runtime rather than at
deploy time — which is why the blocks are written out in full rather than as a
diff against the top level.

### One-time setup per cell

The committed configs carry `<replace-with-…>` placeholders wherever a per-cell
resource id or hostname belongs. Create the resources, then paste the ids in:

```bash
# Per environment; drop the -staging suffix for production.
wrangler d1 create lunora-cloud-staging
wrangler r2 bucket create lunora-cloud-telemetry-staging
wrangler queues create lunora-tenant-queue-staging
wrangler pipelines create lunora-cloud-telemetry-staging
```

`scripts/check-deploy-config.ts` refuses a deploy while any placeholder remains:

```bash
pnpm --filter @lunora/cloud run deploy:check staging
```

That gate exists because wrangler will happily publish a Worker bound to a D1
database that does not exist. The deploy goes green and the first query fails in
production, with nothing pointing back at the config.

Then the Worker secrets, which are never in git and never in the workflow — set
once per cell with `wrangler secret put <NAME> --env <cell>`:

- **Control plane** (`wrangler.jsonc`): `LUNORA_ADMIN_TOKEN`, `AUTH_SECRET`,
  `SECRET_ENCRYPTION_KEY`, `CLOUDFLARE_API_TOKEN`, `GITHUB_WEBHOOK_SECRET`,
  `CREEM_API_KEY`, `CREEM_WEBHOOK_SECRET`, plus the optional
  `LUNORA_TAIL_SECRET`, `R2_SQL_TOKEN`, `RESEND_API_KEY`, `GITHUB_APP_*` and the
  social sign-in pairs. `.dev.vars.example` documents what each one does and, for
  the optional ones, the symptom of leaving it unset.
- **Dispatcher**: `CONTROL_PLANE_TOKEN` (the control plane's
  `LUNORA_ADMIN_TOKEN`) — without it the per-plan runtime limits are not applied.
- **Tail consumer**: `LUNORA_TAIL_SECRET`, the **same value** as on the control
  plane, or `/v1/logs/tail` answers 503 and tenant logs never arrive.

### CI

`.github/workflows/deploy-cloud.yml` deploys on push:

- **`alpha` → `cloud-staging`**, **`main` → `cloud-production`**, and
  `workflow_dispatch` can target either explicitly.
- It fires when `apps/cloud/**`, `packages/**`, `shared/**`, `protocol/**` or the
  lockfile changes. The wider-than-`apps/cloud` path list is deliberate: the
  control plane bundles the workspace packages, so a package change _is_ a change
  to the deployed bytes.
- Each GitHub Environment (`cloud-staging`, `cloud-production`) holds
  `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. The token needs Workers
  Scripts:Edit, Workers KV:Edit, D1:Edit, R2:Edit, Queues:Edit, Workers for
  Platforms:Edit, Account Analytics:Read, and Zone → Workers Routes:Edit for the
  routed zone. Scoping them per environment is what lets production carry a
  required reviewer.
- The gates run as `lunora verify` (wrangler validation, codegen dry-run, the
  ERROR-advisory gate, the schema-drift gate, `tsc --noEmit`) before anything is
  published. Not `lunora deploy`: this app's `main` is a hand-written entry that
  Vite builds, so what ships is `@cloudflare/vite-plugin`'s `dist/server` output,
  and deploying the source config would bundle `src/server.ts` raw — a control
  plane with no studio.
- The control plane picks its cell with **`CLOUDFLARE_ENV=<cell> vite build`**.
  That is how the Vite plugin resolves `env.<cell>` into the deploy config it
  emits at `dist/server/wrangler.json`, which carries no `env` key of its own —
  passing `--env` to the wrangler call instead looks right and does nothing. The
  dispatcher and the tail consumer have no Vite build, so those two deploy
  straight from their source configs with `--env`.
- Set `CLOUD_HEALTH_URL` as a _variable_ on the environment to have every deploy
  probed (`lunora verify --health-url`). Left unset, the run warns that the
  deploy was published without a probe — a cell's reachable origin is not
  derivable from CI.

### Tags and releases

A **production** deploy tags the commit `cloud-v<run-number>` and cuts a GitHub
Release whose notes span back to the previous `cloud-v*` tag. Staging deploys are
not tagged — tagging every `alpha` merge would make `cloud-v*` a commit log
rather than a list of what is actually serving tenants.

The `cloud-v*` namespace is deliberately outside the `@lunora/<pkg>@<version>`
shape `semantic-release` owns: `apps/cloud` is private, never published to npm,
and has no semver of its own, so a tag in that namespace would read to
`multi-semantic-release` as a package release that never happened.
