title: Migrating from Convex
description: Side-by-side mapping — schema, queries, mutations, actions, React hooks.
---

Cirrus borrows Convex's authoring shape on purpose: if you've used Convex, you
already know 80% of Cirrus. The wire transport, runtime, and storage are
different — but the file layout, the `defineSchema` / `query` / `mutation` /
`action` factories and the React hooks are intentionally near-identical.

This guide is a side-by-side mapping plus the specific gotchas you'll hit
when porting an existing Convex app.

## At a glance

| Concern             | Convex                   | Cirrus                                    |
| ------------------- | ------------------------ | ----------------------------------------- |
| Hosting             | Convex Cloud             | Your Cloudflare account                   |
| Backend runtime     | Convex (V8 isolate)      | Cloudflare Workers + Durable Objects      |
| Default storage     | Convex DB                | One Durable Object's SQLite (`__root__`)  |
| Cross-tenant data   | tables                   | `.global()` tables in D1                  |
| Per-tenant data     | tables                   | `.shardBy("field")` tables in DOs         |
| Schema file         | `convex/schema.ts`       | `cirrus/schema.ts`                        |
| Generated API       | `convex/_generated/api`  | `cirrus/_generated/api`                   |
| Function dir        | `convex/*.ts`            | `cirrus/*.ts`                             |
| Codegen trigger     | `convex dev`             | `cirrus codegen` (or the Vite plugin)     |
| React hooks         | `convex/react`           | `@cirrus/react`                           |
| Server SDK          | `convex/server`          | `@cirrus/server`                          |
| Validators          | `convex/values` (`v.*`)  | `@cirrus/values` (`v.*`)                  |
| Auth                | Convex Auth, Clerk, etc. | `@cirrus/auth` (built-in)                 |
| Scheduled functions | `ctx.scheduler.runAfter` | `ctx.scheduler.runAfter` (same shape)     |
| File storage        | `ctx.storage`            | `ctx.storage` (backed by R2)              |
| Subscriptions       | WebSocket                | WebSocket (Durable Object hibernated)     |
| Deploy              | `npx convex deploy`      | `cirrus deploy` (wraps `wrangler deploy`) |

## Schema

The DSL is the same. `defineSchema` and `defineTable` come from
`@cirrus/server`, indexes use the same `(name, fields, { unique? })` shape,
validators are byte-compatible.

Convex:

```ts
import { defineSchema, defineTable } from "convex/server";
import { v } from "convex/values";

export default defineSchema({
    messages: defineTable({
        channelId: v.id("channels"),
        text: v.string(),
    }).index("by_channel", ["channelId"]),
});
```

Cirrus:

```ts
import { defineSchema, defineTable, v } from "@cirrus/server";

export const schema = defineSchema({
    messages: defineTable({
        channelId: v.id("channels"),
        text: v.string(),
    })
        .shardBy("channelId")
        .index("by_channel", ["channelId"]),
});
```

The two new keywords are `.shardBy(field)` and `.global()`. Convex hides this
decision behind its hosted database; Cirrus surfaces it because **the answer
determines which Durable Object owns the row**. See
[Concepts: sharding](/docs/concepts/sharding) for the decision tree.

## Queries, mutations, actions

Same factories, same `(args, handler)` shape, same `ctx` properties.

Convex:

```ts
import { mutation, query } from "./_generated/server";
import { v } from "convex/values";

export const list = query({
    args: { channelId: v.id("channels") },
    handler: async (ctx, { channelId }) => {
        return ctx.db
            .query("messages")
            .withIndex("by_channel", (q) => q.eq("channelId", channelId))
            .collect();
    },
});
```

Cirrus:

```ts
import { mutation, query, v } from "@cirrus/server";

export const list = query({
    args: { channelId: v.id("channels") },
    handler: async (ctx, { channelId }) => {
        return ctx.db
            .query("messages")
            .withIndex("by_channel", (q) => q.eq("channelId", channelId))
            .collect();
    },
});
```

Single import path (`@cirrus/server`) instead of two
(`./_generated/server` + `convex/values`). The body is identical.

## React

```ts
// Convex
import { useMutation, useQuery } from "convex/react";
import { api } from "../convex/_generated/api";

// Cirrus
import { useMutation, useQuery } from "@cirrus/react";
import { api } from "../cirrus/_generated/api";
```

Hook signatures match: `useQuery(api.file.fn, args)` returns `undefined`
while loading, then the typed result; `useMutation(api.file.fn)` returns a
typed function. `usePaginatedQuery` and `useAction` mirror Convex too.

## Auth

Convex pairs with external providers (Clerk, Auth0, Convex Auth). Cirrus
ships [`@cirrus/auth`](/docs/addons/auth) — an opt-in add-on that handles
sessions, password and OAuth flows, and rotating refresh tokens inside a
`SessionDO`. The `ctx.auth` shape is the same.

## Scheduler

`ctx.scheduler.runAfter(ms, fn, args)` works identically. Under the hood
Cirrus persists the schedule in a `SchedulerDO` instead of Convex's hosted
queue.

## File storage

`ctx.storage.generateUploadUrl()` / `ctx.storage.getUrl(id)` mirror the
Convex shape. Cirrus backs them with **R2** — uploads go straight to R2 via
a presigned URL, downloads stream from the Worker.

## Subscriptions

Both products implement the same observable mental model: a query is a
subscription, mutations broadcast deltas, the client re-renders. The
difference is the routing layer — Convex broadcasts via its hosted service,
Cirrus broadcasts via the owning Durable Object using WebSocket hibernation
so idle subscribers cost zero CPU. See [Real-time](/docs/concepts/realtime).

## Porting checklist

1. **Move files**:
    - `convex/` → `cirrus/`
    - `convex/schema.ts` exports default → `cirrus/schema.ts` exports `schema`
2. **Rewrite imports**:
    - `convex/server` → `@cirrus/server`
    - `convex/values` → `@cirrus/server` (or `@cirrus/values`)
    - `convex/react` → `@cirrus/react`
    - `./_generated/server` → `@cirrus/server`
    - `../convex/_generated/api` → `../cirrus/_generated/api`
3. **Decide sharding**: every table needs `.global()`, `.shardBy(field)`, or
   neither (stays in `__root__`). Start with neither; promote when you hit
   the 1 GiB warning. Details: [Sharding](/docs/concepts/sharding).
4. **Generate the initial migration**: any `.global()` table needs an
   `INSERT INTO channels … FROM <exported.jsonl>` step. Run
   `cirrus migrate generate init` to get the schema SQL, then add a
   one-off data-import migration alongside it.
5. **Export Convex data**: `npx convex export` produces a JSONL dump per
   table. Reshape it to your new schema (drop `_creationTime` if you don't
   need it; Cirrus uses `createdAt` columns you populate yourself), then
   batch-insert via a Cirrus mutation or a `cirrus run` script.
6. **Wire the React provider**: replace `<ConvexProvider client={…}>` with
   `<CirrusProvider client={createCirrusClient({ url })}>`. URL is your
   Worker's `*.workers.dev` hostname.
7. **Deploy**: `cirrus deploy` builds, runs migrations, calls
   `wrangler deploy`. Your data plane is now in your own Cloudflare account.

## Caveats

- **No transactions across shards**. A mutation runs inside one Durable
  Object; cross-shard writes need a saga or an action that fans out. Convex
  gives you cross-document transactions inside its DB; Cirrus doesn't.
- **D1 eventual consistency on replicas**. Reads from `.global()` tables
  use the D1 Sessions API. Pass the `x-d1-bookmark` header to get
  read-your-writes; otherwise you may read a slightly stale replica.
- **No managed dashboard**. Use Cloudflare's DO browser, the D1 console,
  and `cirrus run` for ad-hoc RPC. A first-party dashboard is on the roadmap.
