Cirrus apps deploy as a single Cloudflare Worker plus Durable Object class,
D1 database, and R2 bucket bindings. There is nothing else to provision —
no separate API service, no platform sign-up.

## `wrangler.jsonc`

```jsonc
{
    "$schema": "node_modules/wrangler/config-schema.json",
    "name": "my-cirrus-app",
    "main": "src/server/index.ts",
    "compatibility_date": "2026-04-07",
    "compatibility_flags": ["nodejs_compat", "web_socket_auto_reply_to_close"],
    "durable_objects": {
        "bindings": [
            { "name": "SHARD", "class_name": "ShardDO" },
            { "name": "SCHEDULER", "class_name": "SchedulerDO" },
        ],
    },
    "migrations": [{ "tag": "v1", "new_sqlite_classes": ["ShardDO", "SchedulerDO"] }],
    "d1_databases": [{ "binding": "DB", "database_name": "my-cirrus-app", "database_id": "<from-wrangler-d1-create>" }],
    "r2_buckets": [{ "binding": "FILES", "bucket_name": "my-cirrus-files" }],
}
```

## Secrets

### Locally

Local secrets live in `.dev.vars` (gitignored), which `wrangler dev` and the
Vite dev server load automatically. Commit a `.dev.vars.example` listing the
keys your worker needs:

```bash
# .dev.vars.example
AUTH_SECRET="replace-with-openssl-rand-hex-32"
AUTH_URL="http://localhost:5173"
STORAGE_SECRET="replace-with-openssl-rand-hex-32"
```

When you run `cirrus dev` (or start Vite) without a `.dev.vars`, Cirrus offers
to generate one from the example — secret-looking placeholders (`*_SECRET`,
`*_TOKEN`, …) are filled with fresh random values, everything else is copied
verbatim. If `.dev.vars` exists but is missing keys the example lists (e.g. you
enabled a new addon), it offers to append just those. Non-interactive runs (CI)
skip the prompt. You can also manage keys by hand with `cirrus env set NAME VALUE`
/ `cirrus env list`.

To check a `.dev.vars` against its example — missing keys, still-unset
placeholders, stray extras — run `cirrus env doctor`. It exits non-zero when
anything is actionable, so it works as a CI gate or a pre-`dev` sanity check.

### In production

Set with `wrangler secret put`:

```bash
wrangler secret put AUTH_SECRET
wrangler secret put RESEND_API_KEY
wrangler secret put STORAGE_SECRET
```

Or push everything from `.dev.vars` at once with `cirrus env push --yes`.

Cirrus never logs secret values; the `wrangler-validator` plugin warns if a
binding marked `secret: true` in your schema is missing from your secret list.

## Containers

If your app declares [containers](/docs/addons/containers), `wrangler deploy`
also builds each Dockerfile-backed image with your local Docker engine and
pushes it to Cloudflare's registry. `cirrus deploy` runs a Docker preflight
first and stops with an actionable message when an engine isn't available, so
the failure is one line rather than a wrangler stack trace. Images must target
**`linux/amd64`**.

To split image build/push from the Worker deploy (e.g. across CI jobs), use the
`cirrus containers` wrappers:

```bash
cirrus containers build ./containers/transcoder --tag transcoder:v1 --push
cirrus containers images list
```

Container egress is billed separately from Workers — see [Limits](/docs/limits).

## Deploy

```bash
pnpm cirrus deploy
```

This runs:

1. `cirrus codegen` (no-op if up-to-date)
2. D1 migration runner against the bound database
3. a Docker preflight when Dockerfile-backed containers are declared
4. `wrangler deploy` against the resolved Worker (building/pushing container images)

CI should run `cirrus codegen --check` first so a stale `_generated/` is a
build failure, not a deploy that silently uses old types.

## Streaming logs

Tail a deployed Worker's live logs with:

```bash
pnpm cirrus logs                     # pretty-printed live tail
pnpm cirrus logs --format json       # one JSON object per line (pipe to jq)
pnpm cirrus logs --status error      # only failed invocations
pnpm cirrus logs --search "userId"   # substring filter on log messages
```

This wraps `wrangler tail`, so it needs a deployed Worker and your wrangler
config; pass a Worker name as the first argument to override the configured
one, and `--env <name>` to target an environment.

For durable, off-Cloudflare log sinks (Datadog, an HTTP endpoint, R2), forward
tail events to a **consumer Worker** via `tail_consumers` in `wrangler.jsonc`:

```jsonc
{
    // ...
    "tail_consumers": [{ "service": "log-forwarder" }],
}
```

Each entry names a Worker that receives this Worker's logs, exceptions, and
fetch metadata. `@cirrus/config` exports a `withTailConsumer(config, consumer)`
helper that appends an entry idempotently (deduped by `service` + `environment`),
and the wrangler validator flags any `tail_consumers` entry missing its
`service`.

### Logpush

To ship logs to a retention/SIEM sink (R2, HTTP, Splunk, Datadog, S3) without a
consumer Worker, enable [Cloudflare
Logpush](https://developers.cloudflare.com/workers/observability/logs/logpush/)
with a single flag:

```jsonc
{
    // ...
    "logpush": true,
}
```

Cirrus validates that `logpush` is a boolean (a typo like `"logPush"` would
otherwise be silently dropped by wrangler), but the **sink itself is a Logpush
_job_** created in the Cloudflare dashboard or via the API — Cirrus does not
manage job lifecycle. The Studio surfaces both halves: its **Logs → Log drains**
panel renders the `{ "logpush": true }` snippet and deep-links to the Cloudflare
observability dashboard where you create the job. In short: Cirrus validates the
flag; the job lifecycle stays in Cloudflare.
