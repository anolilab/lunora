Cirrus is not a web framework, and it does not want to be one. It is the
**reactive backend that any meta-framework plugs into** — TanStack Start, React
Router, SolidStart, SvelteKit, Nuxt, Astro — composed into **one Cloudflare
Worker**. You keep your framework's routing, rendering, and DX; Cirrus adds
type-safe data and the thing no other backend has: [live loaders](/docs/frameworks/reactive-loaders).

> **Bring your framework. Your loaders are live.**

## One worker, two dispatch flows

A Cirrus worker is created with `createWorker(...)`, which already accepts an
optional `httpRouter` — any object shaped like `{ fetch(request, env?, ctx?) }`.
Every meta-framework's SSR handler is structurally exactly that, so you mount it
as the `httpRouter` and Cirrus dispatches by path:

```ts
import { createWorker } from "@cirrus/runtime";

import { ssrHandler } from "./framework-entry"; // your framework's SSR fetch handler

export default createWorker({
    httpRouter: ssrHandler, // pages / API / SSR loaders ───────┐
    shardDO: ShardDO, //                                        │
    auth, // /api/auth/* ───────────────────────────────────────┤
    // …                                                         ▼
});
```

The worker resolves each request in this order:

1. `/api/auth/*` → `@cirrus/auth`
2. explicit routes → webhooks / callbacks
3. **`httpRouter.fetch`** → your meta-framework's SSR handler (everything else)
4. `/_cirrus/rpc` → query / mutation RPC
5. `/_cirrus/ws` → subscriptions / deltas
6. `/_cirrus/admin/*` → studio / observability

Cirrus realtime is mounted under the reserved **`/_cirrus/*`** namespace, so it
never collides with your framework's routes. Pages and API go to your framework;
queries, mutations, and subscriptions go to `/_cirrus/*`. A 500 from your SSR
handler does not take down the realtime endpoints.

> **Coming soon:** a `composeWorker({ httpRouter, ...cirrusOptions })` helper —
> thin sugar over `createWorker` — so templates read cleanly, plus an in-process
> `serverQuery` fast-path that lets an SSR loader call Cirrus _directly_ inside
> the same worker, skipping the network hop to `/_cirrus/rpc`. Today the HTTP RPC
> path is used; in Cloudflare's module-worker model that's a same-process
> loopback, so latency is already near-zero.

## The per-framework matrix

How a framework composes with Cirrus depends on who owns the worker entry. This
mirrors void's class-a/b/c model.

| Class                                  | Frameworks                                      | Composition strategy                                                                                                                                                                   | Status                                     |
| -------------------------------------- | ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| **A — Vite-native, we own the entry**  | TanStack Start, React Router (Vite), SolidStart | `createWorker({ httpRouter: <framework SSR handler> })` directly in the worker entry. Cleanest tier; in-process `serverQuery` available here.                                          | TanStack Start shipped; others in progress |
| **B — own CF adapter, hook-injection** | SvelteKit, Nuxt, Astro                          | The framework builds its own server; Cirrus composition is injected into its server entry / hooks. Cirrus realtime stays under `/_cirrus/*`; the framework keeps everything else.      | preview                                    |
| **C — non-CF or SSR-less**             | static / SPA                                    | No SSR loaders. Ship the client adapter plus a standalone Cirrus worker (the current default for SPA apps). Data is still live; it just hydrates client-side instead of from the HTML. | shipped                                    |

**Class A** is the cleanest: we own the Cloudflare worker entry, so we drop the
framework's SSR handler straight into `httpRouter`. **Class B** frameworks bundle
their own worker, so Cirrus is injected into their server entry rather than
fighting their build (the adapter ships `withCirrus()`-style wrappers). **Class
C** has no SSR loaders, so there's nothing to make live on the server — the client
adapter still gives you live queries, they just hydrate on the client.

## Client adapters

The browser SDK, `@cirrus/client`, is **framework-neutral** — transport,
subscriptions, the offline queue, delta-merge, and reconnect have zero framework
code. Each adapter is a thin idiomatic layer on top, and every adapter exposes the
same handoff: a live `useQuery`/equivalent, an optimistic `useMutation`/
equivalent, a provider/context, and the preloaded-hydration primitive that seeds
an SSR value into a live subscription.

| Adapter          | Idiom                            | Status      |
| ---------------- | -------------------------------- | ----------- |
| `@cirrus/react`  | hooks + context                  | shipped     |
| `@cirrus/solid`  | signals / resources              | in progress |
| `@cirrus/svelte` | stores (`$store`) / runes        | in progress |
| `@cirrus/vue`    | composables (`ref` / `reactive`) | in progress |

> Solid lands first after React: its fine-grained signals map most directly onto
> Cirrus deltas, so it showcases live loaders with the least glue.

For React today, the preloaded-hydration primitive is `usePreloadedQuery` (see
[Reactive loaders](/docs/frameworks/reactive-loaders)). The Solid/Svelte/Vue
adapters will expose the same hydrate-then-subscribe handoff under their idiom's
name.

## Scaffolding

Scaffold a new project wired for your framework with `cirrus init`:

```bash
cirrus init my-app -t tanstack-start   # class A — shipped, with a live-loader route
cirrus init my-app -t vite             # SPA (class C) — the default
cirrus init my-app -t standalone       # worker-only, no frontend
```

`cirrus init -t tanstack-start` is fully wired: it mounts the framework SSR
handler as the worker's `httpRouter`, ships a sample **live loader** route, and
sets up the `@cirrus/react` provider. Templates for `react-router`,
`solid-start`, `sveltekit`, `nuxt`, and `astro` are in progress and land
alongside their adapters.

To add Cirrus to an **existing** meta-framework app, the in-place patcher
(`cirrus init --here`) wires the worker composition and provider into your project
without scaffolding a fresh tree.

## Vite composition

Under Vite, the Cirrus plugin stacks alongside your framework's plugin so a single
worker is emitted. Pass `cloudflare: false` to let the framework supply its own
Cloudflare/SSR build while the Cirrus plugins (codegen, studio, wrangler
validate/reconcile) run beside it:

```ts
// vite.config.ts
import { cirrus } from "@cirrus/vite";

export default defineConfig({
    plugins: [
        frameworkPlugin(), // your framework's Vite plugin
        cirrus({ cloudflare: false }), // codegen + studio + wrangler reconcile, no CF takeover
    ],
});
```

Framework auto-detection from `package.json` and full one-worker emit for class-A
frameworks are in progress.
