`@cirrus/studio` is a component library for inspecting and operating a Cirrus
backend — a data browser, function runner, metrics, migrations, scheduled jobs,
file browser, and more. Compose the panels yourself behind a `<CirrusProvider>`,
mount the ready-made `<Studio>` shell, or use the batteries-included
`mountStudio` entry.

## Running the studio

Three ways, smallest setup first:

1. **`cirrus dev` (zero config).** The `@cirrus/vite` plugin serves the studio
   at **`/__cirrus`** during dev and prints the URL on startup. Add
   `@cirrus/studio` to your project's deps and it just works; opt out with
   `cirrus({ studio: false })`.
2. **Standalone app.** `apps/studio` is a deployable Vite SPA that points at
   any worker via `VITE_CIRRUS_URL` — for hosting the studio separately from
   dev.
3. **Embed.** Mount `<StudioApp baseUrl="…" />` or compose individual panels
   under your own `<CirrusProvider>`.

```ts
// mount the whole app into a <div id="root">
import { mountStudio } from "@cirrus/studio/mount";

mountStudio({ baseUrl: "https://my-app.workers.dev" });
```

## Panels

- `DataBrowser` — list a shard's tables and page through their rows (table/JSON
  toggle), with optional row insert/patch/delete.
- `GlobalDataBrowser` — the same, for `.global()` (D1-backed) tables.
- `SchemaViewer` — every table with its row count, expandable to its columns.
- `FunctionRunner` — pick a registered function, edit its JSON args, and invoke
  it (query / mutation / action).
- `MetricsPanel` — per-shard health: request/error counts, uptime, DB size, and
  reactive-cache hit rate.
- `MigrationsPanel` — inspect data-migration run-state and kick off a migration.
- `ExportImportPanel` — snapshot a shard to NDJSON and restore it.
- `FileBrowser` — page through storage (R2) objects by prefix.
- `ScheduledJobs` — view and cancel functions queued via `runAfter` / `runAt`.
- `UsersPanel` — browse auth users and their sessions (read-only).
- `LogsPanel` — tail the shard's recent log ring buffer.

## Admin gate

The studio reaches the backend two ways: reserved `__cirrus_admin__:*` RPCs
that `ShardDO` intercepts (data, schema, metrics, logs, migrations, export), and
admin-gated worker endpoints under `/_cirrus/admin/*` for things that live
outside the shard (scheduler, storage, functions, global tables, auth).

**Both are disabled unless the server sets `CIRRUS_ADMIN_TOKEN`**, and the client
must present a matching `Authorization: Bearer` token. The components issue no
credentials of their own — configure the client's auth token at the host.

```ts
// worker entry — every admin surface is gated by adminToken
createWorker({
    shardDO: env.SHARD,
    adminToken: env.CIRRUS_ADMIN_TOKEN,
    schedulerDO: env.SCHEDULER, // enables the scheduled-jobs tab
    functions: CIRRUS_FUNCTIONS, // enables function discovery
    storageList: createStorage({ bucket: env.FILES }).list, // enables the file browser
});
```

`globalIntrospector` (D1 tables) and `authAdmin` (the user-management + organization
dashboard, via `@cirrus/auth`'s `createAuthAdmin(auth)`) wire up the remaining tabs;
see the package README for the full per-tab configuration. The auth dashboard is
capability-driven — it shows only the surfaces whose better-auth plugin is enabled.
Tabs whose data source isn't configured are omitted from the `<Studio>` shell.

## Optional-package nav gating

The studio also hides the nav pages for optional `@cirrus/*` packages your app
doesn't use — Payments, Mail, Files + Access Rules, Vectors, and Scheduler — so
you never land on a page that errors with "unknown table". This is automatic:
codegen statically detects which features a deployment wires up and emits the
result into the generated `ShardDO`, which the studio reads once over the
`__cirrus_admin__:studioFeatures` RPC.

A feature's page shows when **any** of these is true:

- a `cirrus/` source imports its package (e.g. `@cirrus/mail`) or reads its
  context helper (`ctx.payments`, `ctx.storage`, `ctx.vectors`, `ctx.scheduler`);
- a schema signal implies it — a `v.storage()` column or storage access rule
  (Files), a declared cron (Scheduler), or a vector index (Vectors);
- the package is a declared dependency in your `package.json` — so a package
  wired only in your worker entry (outside `cirrus/`), like `@cirrus/mail`, still
  shows its page.

The gating **fails open**: every page stays visible until the RPC resolves, and a
worker predating the RPC (or one that errors) keeps showing everything. A page is
only ever hidden once the worker positively reports its feature as unused — so the
worst case is an extra empty page, never a missing working one. No configuration
is required; re-run codegen (`cirrus dev` does this on save) after adding or
removing a package and the nav updates itself.
