`@cirrus/cli` is the standalone alternative to the Vite plugin. It powers
the `cirrus` binary you got when you ran `pnpm create cirrus@latest`. The
plugin and the CLI share the same `@cirrus/codegen` core, so the generated
files are identical regardless of how they were produced.

## Commands

```bash
# Project
cirrus init [name] [-t <template>]      # scaffold a new project (default template: vite)
cirrus view [--remote]                  # open the Cirrus studio in your browser
cirrus docs [section]                   # open the docs site in your browser
cirrus info [--json]                    # print versions, wrangler summary, schema overview
cirrus registry <add|list|view|build>   # component registry

# Develop
cirrus dev [--port n] [--worker-port n] # wrangler worker + studio + codegen watch
            [--no-studio] [--no-codegen]
cirrus codegen [--api-spec <spec>]      # one-shot codegen
cirrus run <fn> [--args <json>]         # send a single RPC to a running worker
            [--shard <key>] [--url <u>]
cirrus reset [--all] [--yes]            # clear local Miniflare state

# Deploy
cirrus prepare [--api-spec <spec>]      # codegen + wrangler validation — for CI
cirrus deploy [--env <name>]            # codegen, validate wrangler, then wrangler deploy
              [--migrate] [--api-spec]
cirrus verify [--api-spec <spec>]       # dry-run codegen + tsc --noEmit (no files written)
              [--no-typecheck]
cirrus analyze [--json]                 # wrangler dry-run: bundle size + top modules

# Data
cirrus logs [worker]                    # stream live Worker logs via wrangler tail
            [--format <pretty|json>]    #   [--status <s>] [--search <q>] [--env <n>]
cirrus migrate <generate|create|up|down|status> [name|id]
cirrus env <list|get|set|unset|push|doctor>
cirrus export [--out <file>] [--tables <t1,t2>] [--url <u>] [--token <tok>]
cirrus import <file> [--table <name>] [--batch-size n]
cirrus backup <create|list|restore|pitr> [--dir <d>] [--at <iso>]
```

### `cirrus init`

Scaffolds a new Cirrus project by fetching a template from
`gh:anolilab/cirrus/templates/<type>#<version>`. Pass `-t` / `--template`
to choose the starting point:

| Template         | Description                                                                                    |
| ---------------- | ---------------------------------------------------------------------------------------------- |
| `vite`           | React + Vite + the Cirrus plugin (the default)                                                 |
| `standalone`     | Worker-only, no frontend                                                                       |
| `tanstack-start` | TanStack Start + the standalone CLI                                                            |
| `next`           | Next.js + the standalone CLI — **not yet available**; re-run with `-t vite` or `-t standalone` |

Additional flags:

- `--from <dir>` — copy from a local templates root instead of fetching remotely (offline-friendly; expects `<type>/` subdirs)
- `--source <ref>` — override the remote template source (e.g. `gh:owner/repo/sub#ref`)
- `--allow-unsafe-source` — permit `--source` values outside `gh:/github:/https://`
- `--here` — add Cirrus to an existing project: detect the framework, patch the config, scaffold `cirrus/`, print per-framework wiring steps

### `cirrus dev`

Starts three concurrent processes: `wrangler dev` (Worker), the embedded
Cirrus studio, and codegen in watch mode. All three reload on file changes.

```bash
cirrus dev                # default ports: studio 6173, worker 8787
cirrus dev --port 7000    # custom studio port
cirrus dev --no-studio    # Worker + codegen only
```

### `cirrus deploy`

Runs codegen, validates `wrangler.jsonc`, then invokes `wrangler deploy`.
Pass `--migrate` to apply pending data migrations against the live worker
immediately after a successful deploy.

```bash
cirrus deploy
cirrus deploy --env staging
cirrus deploy --migrate --migrate-token $CIRRUS_ADMIN_TOKEN
```

### `cirrus prepare`

Same pipeline as `cirrus deploy` but stops before `wrangler deploy` — no
Vite step, no network traffic. Use it in CI to catch codegen drift and
`wrangler.jsonc` validation errors before the deploy job runs.

### `cirrus verify`

Validates `wrangler.jsonc`, runs a codegen dry-run, and type-checks the
project with `tsc --noEmit`. Nothing is written to disk. Exits non-zero on
any error so you can gate merges on it.

### `cirrus migrate`

Manages both schema migrations (D1 SQL) and online data migrations (row
transforms that run against a live worker):

```bash
cirrus migrate generate add_email_index   # diff schema.ts → emit D1 SQL
cirrus migrate create --name backfill_at  # scaffold a data-migration stub
cirrus migrate up                         # run pending data migrations (dev)
cirrus migrate up --prod --url <url>      # run against production (requires --yes)
cirrus migrate status                     # show pending / applied / failed
```

`generate` parses `cirrus/schema.ts`, filters to `.global()` tables (sharded
tables live in per-DO SQLite — no migration needed), diffs against
`cirrus/migrations/.snapshot.json`, and emits a timestamped SQL file. Commit
both the SQL and the snapshot — they are deterministic.

### `cirrus run`

Send a single RPC to a running Worker without spinning up the client SDK:

```bash
cirrus run messages:send --args '{"channelId":"general","text":"hi"}'
```

`--shard` overrides shard routing; `--url` lets you point at a deployed
Worker instead of `http://localhost:8787`.

### `cirrus env`

Manage `.dev.vars` (local secrets) and push them to Cloudflare via `wrangler secret`:

```bash
cirrus env list              # list all keys in .dev.vars
cirrus env get DATABASE_URL  # read a single key
cirrus env set FOO bar       # write a key
cirrus env unset FOO         # remove a key
cirrus env push              # upload to Cloudflare (prompts unless --yes)
cirrus env push --prod --yes # push to the production environment
cirrus env doctor            # validate .dev.vars against wrangler.jsonc bindings
```

### `cirrus export` / `cirrus import`

Bulk data transfer between workers — mirrors Convex's `convex export` /
`convex import`:

```bash
cirrus export --out ./backup.ndjson
cirrus export --tables messages,channels --url https://my-worker.workers.dev --token $TOKEN

cirrus import ./backup.ndjson
cirrus import ./users.ndjson --table users   # wrap bare docs as {table,doc} envelopes
```

### `cirrus backup`

Managed snapshot backups and native point-in-time recovery (PITR):

```bash
cirrus backup create                   # snapshot the running shard
cirrus backup list                     # list available snapshots
cirrus backup restore <id>             # restore a snapshot
cirrus backup pitr --at 2024-06-01T12:00:00Z   # read PITR bookmark
cirrus backup pitr --at 2024-06-01T12:00:00Z --restore --yes   # restore to that point
```

### `cirrus registry`

Fetch and manage reusable Cirrus components (queries, mutations, UI widgets):

```bash
cirrus registry list
cirrus registry view auth/session-token
cirrus registry add auth/session-token
cirrus registry build   # regenerate the local catalog index.json
```

### `cirrus analyze`

Runs a `wrangler` dry-deploy and reports bundle size, the heaviest modules,
and the state of `_generated/` files. Pass `--json` to pipe the output to a
CI artifact.

### `cirrus logs`

Streams live logs from a deployed Cirrus Worker by wrapping `wrangler tail`:

```bash
cirrus logs
cirrus logs my-worker --format json --status error
cirrus logs --search "auth" --env staging
```

## Writing Cirrus functions by hand

Queries, mutations, and actions are plain TypeScript files under `cirrus/`.
There is no scaffolding command — create the file yourself:

```ts title="cirrus/messages.ts"
import { mutation, query, v } from "@cirrus/server";

export const list = query({
    args: { channelId: v.id("channels"), limit: v.optional(v.number()) },
    handler: async (ctx, { channelId, limit }) => {
        return ctx.db
            .query("messages")
            .withIndex("by_channel", (q) => q.eq("channelId", channelId))
            .order("desc")
            .take(limit ?? 50);
    },
});

export const send = mutation({
    args: { channelId: v.id("channels"), text: v.string() },
    handler: async (ctx, { channelId, text }) => {
        await ctx.db.insert("messages", {
            channelId,
            userId: ctx.auth.user!.id,
            text,
            createdAt: Date.now(),
        });
    },
});
```

After saving, `cirrus dev` picks up the change and re-runs codegen
automatically. Run `cirrus codegen` once manually if you are outside the dev
loop.

## Codegen output

`cirrus/_generated/`:

- `api.ts` — the typed `api.<file>.<function>` namespace
- `server.ts` — `internalQuery`, `internalMutation` exports re-typed against your schema
- `dataModel.ts` — `Doc<"messages">`, `Id<"users">`, etc.

These files are deterministic — commit them. CI re-runs codegen and diffs
the result to catch drift.
