title: Data masking
description: Column-level redaction on the read path — the companion to row-level security.
---

Dynamic data masking controls **which column values** a caller sees in the
clear. Where [row-level security](/docs/concepts/rls) decides _which rows_ a
procedure returns, masking decides _which fields_ within those rows come back
redacted. Both are server-side, both attach to a procedure's `.use(...)` chain,
and both are **opt-in per procedure**: a procedure without `.use(mask(...))`
sees raw values, even if another procedure masks the same column.

```ts
import { mask } from "lunorash/server";

import { query } from "./_generated/server";

export const listUsers = query.use(mask({ users: { email: "redact" } })).query(async ({ ctx }) => ctx.db.users.findMany());
// every `email` in the result comes back as null
```

## Strategies

A policy maps `table → column → strategy`. Three strategies:

| Strategy   | Result                                                                                                                                                                                                                                |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `"redact"` | The value becomes `null`. Simplest and safest.                                                                                                                                                                                        |
| `"hash"`   | A deterministic, non-reversible token (FNV-1a). The same input always yields the same token, so values stay **joinable/groupable** client-side without revealing the original. Not cryptographic; it's a masking token, not a digest. |
| `MaskFn`   | A custom transform `(value, context) => masked` that can branch on the caller's roles or sibling columns.                                                                                                                             |

```ts
export const listUsers = query
    .use(
        mask({
            users: {
                email: "redact",
                phone: "hash",
                ssn: (value, { auth }) => (auth.can("pii:view") ? value : "•••"),
            },
        }),
    )
    .query(async ({ ctx }) => ctx.db.users.findMany());
```

## Roles and bypass

A `MaskFn` receives a context with an `auth` view (`auth.can(permission)`,
`auth.roles`, `auth.userId`, `auth.identity`), so masking can be role-aware. Wire
the permissions that back `auth.can(...)` through the `roles` option, and use
`bypass` to skip masking entirely for privileged callers:

```ts
import { mask, definePermission, defineRole } from "lunorash/server";

import { query } from "./_generated/server";

const viewPii = definePermission("pii:view");
const support = defineRole("support", { permissions: [viewPii] });

export const listUsers = query
    .use(
        mask(
            { users: { email: "redact", phone: "redact" } },
            {
                roles: [support],
                bypass: ({ auth }) => auth.can("pii:view"), // privileged callers see raw values
            },
        ),
    )
    .query(async ({ ctx }) => ctx.db.users.findMany());
```

A `MaskFn` also sees the **original, un-masked row** as `context.row`, so it can
branch on a sibling column:

```ts
mask({
    users: {
        // hide email unless the row itself is an admin account
        email: (value, { row }) => (row?.role === "admin" ? value : null),
    },
});
```

## What's masked, what isn't

- **Read path is wrapped.** `get`, `findFirst`/`findFirstOrThrow`, `findMany`, the
  `query().withIndex().order().collect()/first()/take()/paginate()` chain, and
  `rankPage` all rewrite the declared columns of each **top-level** row.
- **Nested relations are not masked.** Rows hydrated through a `with` clause sit
  below the facade the mask wraps, the same boundary RLS draws.
- **Writes pass through untouched.** `insert`, `patch`, `replace`, and `delete`
  are never wrapped; stored data is never altered. Masking is an output filter.
- **Aggregates fail closed.** `aggregate()` and `groupBy()` over a masked column
  throw `MASK_UNSUPPORTED` (HTTP 422): a group key _is_ the raw value and an
  aggregate is computed _from_ it, so neither can be served without leaking.
- **Filtering and sorting by a masked column fail closed too.** A `where` /
  `filter` that references a masked column also throws `MASK_UNSUPPORTED`
  (HTTP 422), on `findMany`, `findFirst`, and `count` alike. A predicate like
  `where: { ssn: { eq: X } }` (row present ⇒ value confirmed) or a range check
  turns the mask into a value oracle, so it is rejected. You can't filter or
  sort by a value the mask hides. The server-injected RLS filter is exempt: it
  is server-trusted, not a caller-supplied oracle.
- **Plain counts still work.** A `count`, `rank`, or `rankBefore` that returns a
  count of rows (no column value, no masked-column `where`) passes through; only
  a `count` whose `where` references a masked column throws.
- **A throwing `MaskFn` redacts to `null`.** It never leaks the raw value.

## Sensitive arguments

Masking covers what a procedure _returns_. A value a caller _sends_ (a password,
an API key a person typed in) is marked on the argument itself with
`v.sensitive(...)`:

```ts
const storeKey = mutation.input({ label: v.string(), apiKey: v.sensitive(v.string()) });
```

The marker follows the value, not the name. The request log and the Studio run
history keep `«sensitive»` in its place, the validation error does not echo it,
the JSON Schema marks it `writeOnly`, and the generated client never queues the
call offline. The name carries no weight: `value` is protected exactly as
`apiKey` is.

Within that call, the value is also scrubbed from what the handler itself
records: `ctx.log` lines, `ctx.trace` spans and their errors, the `ctx.span`
wide event, `ctx.fetch` spans, `ctx.metrics` attributes, `ctx.db` failure
messages and the dispatch's root span. A composed call (`ctx.runQuery`,
`ctx.runMutation`, `ctx.runAction`) runs inside the same call, so the callee's
own marked arguments are scrubbed as well. A value of four or more characters is
replaced wherever it appears in a recorded string. A value of three characters (a
CVV or a three-digit PIN) is replaced wherever it appears as a whole word or number,
so `invalid code 123` loses the `123` but `1234` is left alone. A value of one or
two characters is replaced only when it is the whole string, because a single digit
replaced inside text would erase every standalone digit from the line.
A value of four or more characters is also matched in its JSON-escaped spelling (a newline
written as `\n`, a quote as `\"`), because a handler that logs `JSON.stringify(args)` never
writes the raw form. A shorter value is not, so escaping cannot push it into a looser rule.
A marked value is also masked when it is used as a field or attribute name. A property
name of a marked object is masked as a whole name, and two names that mask to the same
placeholder are kept apart with a `#2`, `#3` suffix rather than one overwriting the other.
A span, fetch or database call still in flight when the call returns is scrubbed when it
is recorded, and the value is forgotten then. Nothing else outside the call keeps it.

The scrub does not yet cover a live subscription's re-runs: their records carry
the arguments as the subscription sent them.

## Tooling

- **Studio**: the [data browser](/docs/packages/studio#database) shows a "Mask
  sensitive columns" toggle that previews redact/hash/custom output client-side
  and flags masked columns in the grid header. Codegen emits the
  `(table, column, strategy)` map it reads.
- **Advisor**: the [`mask_uncovered_pii_column`](/docs/concepts/advisors) lint
  warns when a **public** procedure reads a table whose columns are masked
  elsewhere but the procedure has no `.use(mask(...))`, the opt-in gap that
  would return PII in the clear.
