The Lunora cloud is both a Workers-for-Platforms control plane **and** a managed
[OpenTelemetry](/docs/concepts/observability) backend. When you deploy an app to
it, the platform wires your telemetry end-to-end for you. There is no collector
to run, no ingest endpoint to configure, and no keys to copy. Your app's spans,
logs, metrics, and AI generations land in the cloud and show up in the dashboard.

If you self-host instead, everything here still works: you point
[`otlpSink`](/docs/concepts/observability#otlpsink) at your own collector. This
page is about the hosted experience.

## How telemetry reaches the cloud

At deploy time the platform injects three things into your tenant Worker:

| Injected               | As            | Purpose                                                |
| ---------------------- | ------------- | ------------------------------------------------------ |
| `LUNORA_OTLP_ENDPOINT` | env var       | this cell's ingest base URL                            |
| `LUNORA_OTLP_TOKEN`    | secret        | a **scoped ingest key** (telemetry-only, can't deploy) |
| `lunora-log-tail`      | tail consumer | streams `ctx.log` output to the Logs store             |

Your app reads the first two in the usual sink wiring, with no cloud-specific
code:

```ts
import { combineSinks, createWorker, otlpSink } from "@lunora/runtime";

export default createWorker({
    // …schema, functions…
    observability: combineSinks(otlpSink({ endpoint: env.LUNORA_OTLP_ENDPOINT, token: env.LUNORA_OTLP_TOKEN })),
});
```

Everything the framework emits flows over the
[standard OpenTelemetry Protocol (OTLP) contract](/docs/concepts/observability#the-wire-contract) to the
cloud: one `SERVER` span per RPC, nested
[`ctx.trace`](/docs/concepts/observability#tracing-sub-operations-with-ctxtrace)
spans, [`ctx.log`](/docs/concepts/observability#structured-logging-with-ctxlog)
lines, [`ctx.metrics`](/docs/concepts/observability#application-metrics-with-ctxmetrics),
and [AI generation spans](/docs/concepts/observability#generation-spans-ai).

## Traces

The **Traces** tab is a real-duration, nested trace waterfall over the span
store. Pick a project, then a deployment; recent traces list newest-active first
with their latency, span count, error count, and root operation.

Open a trace to drill into its **waterfall**: every span placed on the trace
timeline by its true start and duration, indented by its depth under
`parentSpanId`, so you see which part of a request took the time (not just that it
took 900 ms). An **errors-only** toggle narrows the list; the query also supports
filtering by duration, function path, and time window.

**Generation spans.** An AI model call shows a `gen` chip with the model and its
token counts (`12→34 tok`). Click any span to open the **detail pane**: its id,
duration, status, attributes, and, for a generation, the model, prompt/completion
tokens, and (when the emitter opted in) the recorded input/output. See
[generation spans](/docs/concepts/observability#generation-spans-ai) for how
`@lunora/ai` and `@lunora/agent` produce them.

## Issues

Error spans (`status.code === 2`) are grouped into **Issues** by a deterministic
[fingerprint](/docs/concepts/error-handling), with a count, first/last-seen,
and a sample message. Container crashes additionally open **Incidents**.

## Logs

Every `ctx.log` line is streamed to the durable Logs store via the tail consumer,
keeping its full shape: the seven-tier severity, the rendered message, the
structured `fields`, the `functionPath`, and the `traceId`/`spanId`. The Logs tab
filters by severity, function, free-text search, and trace id, so you can pull up
exactly the lines for one dispatch and link a line back to its trace.

## Metrics

`ctx.metrics.*` measurements POST to `/v1/metrics`. Keep attributes low-cardinality; see the
[metrics guidance](/docs/concepts/observability#application-metrics-with-ctxmetrics).

## Scoped ingest keys

Deploy keys have a **capability**:

- **`deploy`** (the default): the full key your CI uses to `lunora deploy`.
- **`ingest`**: telemetry-only. It can push to the OTLP endpoints but is
  **rejected by the deploy and admin paths**, so a leaked ingest token can't ship
  code.

The platform mints one ingest key per org and injects it as `LUNORA_OTLP_TOKEN` at
deploy time. You never handle it directly for your own apps.

## Bring your own OpenTelemetry

The cloud ingest is a standard OTLP endpoint, so **any** OpenTelemetry SDK or
Collector can ship to it, not only Lunora's `otlpSink`. Issue an `ingest`-scoped
key and point your exporter at the cell's base URL:

| Endpoint      | Signal  |
| ------------- | ------- |
| `/v1/traces`  | spans   |
| `/v1/logs`    | logs    |
| `/v1/metrics` | metrics |

Lunora's own sinks send JSON, gzipped once the body is large enough.
Authenticate with `Authorization: Bearer <ingest-key>`.

## Retention and redaction

The dashboard reads recent traces and logs from the cloud's hot store. Sensitive
attribute and log-field values (anything keyed like a credential) are redacted by
the sink in your Worker before they are sent.
