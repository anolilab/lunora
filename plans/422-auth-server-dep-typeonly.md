## Why this matters

`packages/auth/package.json:120` exact-pins `"@lunora/server": "1.0.0-alpha.78"` in `dependencies`. Because it is exact-pinned, an app on any newer `@lunora/server` gets a **second copy** installed — which is how two incompatible `Middleware`/`TableDefinition` type identities end up in one build. The repo's convention for sibling packages that consume `@lunora/server` (`packages/cloudflare-access/package.json:74-92`, likewise `replica`, `seed`) is a `devDependencies` pin plus a `peerDependencies` range `>=1.0.0-alpha.24 <2.0.0-0`, so the consumer's single copy is used. `middleware.ts:6-9` even hand-mirrors `MiddlewareNext` specifically to avoid a runtime dependency — the manifest contradicts the package's own documented intent.

**Evidence correction from the audit**: imports are NOT all type-only — `packages/auth/src/schema.ts:2` value-imports `defineTable` from `@lunora/server`. That changes the fix from "optional peer" to "**required** peer": the consumer must provide `@lunora/server` (every Lunora app already does), and the peer must NOT be marked optional, because `authTables` (schema.ts) is a core surface of this package.
