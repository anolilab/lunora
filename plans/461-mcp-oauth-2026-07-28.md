# Plan 461 — MCP OAuth: close the MCP 2026-07-28 authorization gaps on better-auth

**Baseline:** `f79680910` (2026-10-02)
**Status:** DONE on `feat/mcp-oauth-2026-07-28` (A–D shipped; B and D after the
user approved the recommended designs. E's metadata scenario passes through the
worker locally; the CI job stays a follow-up until an example app wires `mcp()`,
see §5 E)

## 0. Headline finding

Cloudflare shipped [`@cloudflare/workers-oauth-provider` 1.x](https://developers.cloudflare.com/changelog/post/2026-10-01-workers-oauth-provider-1x/)
(changelog 2026-10-01; npm `1.0.0` on 2026-09-24, `latest` is `1.2.1` from
2026-09-28). It splits into `OAuthAuthorizationServer` and `OAuthResourceServer`
and implements the [MCP 2026-07-28 authorization spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization):
CIMD, RFC 9207 issuer identification, `insufficientScope()` step-up,
`validateToken` over a service binding, `refreshTokenIdleTTL` and
`purgeExpiredData()`.

**The library Lunora already pins, better-auth 1.7.3, implements almost all of
the same spec.** It sends RFC 9207 `iss` and advertises it. It serves RFC 9728
metadata. It has an `insufficient_scope` 403 path. It ships CIMD as
`@better-auth/cimd`, whose `metadataProfile: "mcp-2026-07-28"` is named after
this spec revision. Switching authorization layers would not buy compliance.

Lunora's MCP OAuth falls short of the spec because of **gaps in how Lunora wires
better-auth**, not because of better-auth itself:

1. **CIMD is off on purpose, so no client can register itself.** Our docs say
   Workers can't meet `@better-auth/cimd`'s transport contract
   (`packages/mcp/docs/index.mdx:408-411`), and DCR is off by default. That
   leaves pre-registration as the only path, so Claude, ChatGPT and other
   MCP hosts can't connect unassisted. Cloudflare's own package answers the
   Workers question: it enables CIMD on Workers with only the
   `global_fetch_strictly_public` compatibility flag (`workers-oauth-provider`
   `dist/oauth-provider.d.ts:1110-1114`, `dist/oauth-provider.js:4332`).
2. **Discovery documents probably 404 at the URLs the spec requires.**
   Lunora sends only `/api/auth/*` to better-auth (`packages/auth/src/handler.ts:36`,
   `packages/auth/src/do-wiring.ts:217`, `packages/codegen/src/emit-app.ts:989`).
   The `resource_metadata` URL in the 401 challenge points at
   `/.well-known/oauth-protected-resource/<path>` on the origin root
   (`@better-auth/oauth-provider` `resource-challenge-*.mjs:52`), and that
   path never reaches the plugin that serves it (`@better-auth/mcp`
   `dist/index.mjs:192`).
3. **No step-up.** A read-only token never learns that writes exist. The
   write tools are left out of `tools/list` instead of being challenged with
   `403 insufficient_scope scope="lunora:write"`.
4. **The documented wiring is unverified, and probably broken twice over.** The
   example passes `resource` to `mcp()` but not to `requireMcpAuth`, so
   verification falls back to `audience = baseURL` (`@better-auth/mcp`
   `dist/index.mjs:231-232`), which differs from the token's `.../mcp`
   audience. It also requires `lunora:read`, a scope the example's `mcp()`
   never declares. The only test replaces the whole gate with a double
   (`packages/mcp/__tests__/authed-http.test.ts:41-58`).

**Recommendation:** stay on better-auth and close these four gaps (decision 1),
and do not adopt `workers-oauth-provider` (decision 2). The one idea worth
taking from it is the `global_fetch_strictly_public` answer to SSRF on Workers.

## 1. Current state (audit)

### Lunora surface

- `@lunora/mcp` serves OAuth-protected Streamable HTTP through
  `createAuthedMcpFetchHandler({ protect, server })`
  (`packages/mcp/src/authed-http.ts:153-161`). `protect` is a structural
  lambda, `(handler: (req, claims) => Promise<Response>) => McpFetchHandler`
  (`authed-http.ts:91`). It is typed structurally so that `@lunora/mcp` has no
  dependency on better-auth (`authed-http.ts:79-90`). `server` may be a
  function of the claims, and `mcpTokenScopes` parses `scope` into a set
  (`authed-http.ts:128-134`).
- Every request goes through `serveStateless`, which uses a stateless transport
  with JSON responses, a body bounded while streaming, and no batches
  (`packages/mcp/src/serve-stateless.ts:201-265`). `readScreenedBody` is
  exported, so a gate can read the JSON-RPC message before dispatch. The paid
  gate already does this (`packages/mcp/src/paid.ts:407`).
- Writes are gated on `allowWrites`, resolved per request. The tool list
  (`packages/mcp/src/server.ts:194`) and dispatch (`server.ts:210`) both read
  it. Past that, the write-confirmation digest binds intent but not identity:
  it is keyed by the admin bearer that every OAuth principal shares
  (`packages/mcp/src/write-confirmation.ts:36-43`).
- `@lunora/auth/plugins` re-exports `mcp`, `requireMcpAuth` and
  `createMcpProtectedRequestHandler` from `@better-auth/mcp`
  (`packages/auth/src/plugins.ts:91`), `oauthProvider` (`:96`) and `jwt`
  (`:128`). It does **not** re-export `cimd` (see
  `packages/mcp/docs/index.mdx:408-411`) or `oauthProviderAuthServerMetadata`.

### Client side: `@lunora/agent`

`mcpTools({ url })` builds `new StreamableHTTPClientTransport(url)` with **no
`authProvider`** (`packages/agent/src/mcp.ts:175-177`). An agent therefore
can't reach an OAuth-protected MCP server at all, except through an injected,
pre-connected `client` (`mcp.ts:59`). CIMD is a client-registration mechanism
for an interactive authorization-code flow. An unattended durable agent has no
browser to complete one, so **CIMD on the agent side is not a gap in this
plan**. It belongs with "agent connects to OAuth MCP servers", which nobody has
asked for (§9 Q5).

## 2. Existing seams (do not reinvent)

- **The `protect` lambda** (`authed-http.ts:91`). Every authorization layer
  plugs in here, and `@lunora/mcp` stays free of auth dependencies. Step-up
  works inside it: better-auth's gate already turns a thrown insufficient-scope
  error into the 403 challenge (`@better-auth/mcp` `index.mjs:78-83`).
- **`readScreenedBody`** (`serve-stateless.ts:146-177`). It reads the
  JSON-RPC message once, with the size bound, before dispatch. This is how the
  paid gate prices a `tools/call` (`paid.ts:407`), and step-up needs to see the
  tool name the same way.
- **`@lunora/auth/plugins` as the curated re-export point** (`plugins.ts`). New
  better-auth surfaces (`cimd`, `oauthProviderAuthServerMetadata`) go through
  it, under the exact pins in `catalog:auth`.
- **`handleAuthRequest` / `isAuthRoutePath`** (`handler.ts:19-41`), used by both
  D1 mode and DO mode (`do-wiring.ts:217`). The well-known routing fix goes in
  this one predicate, not in a second router.
- **better-auth's own discovery exports**: `oauthProviderAuthServerMetadata`
  (`authorize-*.mjs:806-821`) and `mcp()`'s `onRequest`. Route requests to
  them; never hand-build a metadata document.

## 3. The behavioural contract to preserve

- An unauthenticated request never constructs a `LunoraClient` or MCP server
  (`authed-http.test.ts` "refuses an unauthorized request…").
- `createAuthedMcpFetchHandler`'s options and exports are unchanged. `@lunora/mcp`
  gains no runtime or type dependency on better-auth or on Cloudflare packages
  (`authed-http.ts:79-90`).
- Requests with a batch or an oversized body are refused for authorized callers
  exactly as before (`serve-stateless.ts:201-223`).
- DCR stays off by default. CIMD stays **opt-in**: no app that hasn't asked for
  it starts fetching URLs it was handed.
- Requests under `/api/auth/*` route as before. Widening routing adds only
  the exact well-known paths that a configured `mcp()` / `oauthProvider`
  serves, and never a `/.well-known/*` prefix (other apps own
  `/.well-known/` paths such as `security.txt`).

## 4. Design decisions

1. **Stay on better-auth and close the gaps (option a).** better-auth 1.7.3
   already implements the 2026-07-28 rows of §1 that matter: CIMD with the MCP
   profile, RFC 9207, RFC 9728, 403 step-up and audience binding. Lunora's
   users and sessions already live in it, and the OAuth clients and consents
   share that store (`oauthClient` already has `clientDiscoveryId` for CIMD
   provenance, `@better-auth/oauth-provider` `oauth-*.d.mts:22`). It is
   maintained and pinned, which satisfies "reach for a maintained dependency".
   _Rejected:_ hand-rolling CIMD or PRM serving, because better-auth already
   ships both.
2. **Do not adopt `workers-oauth-provider` (option b), and do not run both
   (option c).** Its authorization server keeps clients, grants and tokens in
   an `OAUTH_KV` namespace with props encrypted per token (`d.ts:1883`;
   `docs/resource-servers.md` "Separate Workers"). Adopting it as the
   authorization server would give Lunora a **second OAuth client/consent
   store** next to better-auth's. User sign-in still has to come from
   better-auth through its `/authorize` route, so every MCP grant would cross
   two identity systems. It is also Cloudflare-only by construction (KV, the
   `Cloudflare.compatibilityFlags` probe, the `caches` API). As an
   `OAuthResourceServer` in front of better-auth tokens it would only replace
   `requireMcpAuth` with an equivalent that validates the same JWTs. Nothing
   in §1 is a gap that it closes and better-auth does not.
   _Rejected:_ a `@lunora/mcp` adapter for it "for choice", which is an
   extension point with no second user. The `protect` seam already takes any
   gate, so a user who wants it can wire `OAuthResourceServer` themselves
   (§9 Q3 decides whether that gets a docs recipe).
3. **CIMD on Workers uses a `global_fetch_strictly_public` transport,
   borrowed from Cloudflare's own posture.** `@better-auth/cimd` asks the app
   for `fetchClientMetadataResource`, a transport that resolves the host once,
   rejects RFC 6890 addresses, pins the connection and refuses redirects
   (`index.d.mts:71-78`). On Workers the redirect half is already enforced by
   cimd itself (`redirect: "error"` plus a `response.redirected` check,
   `index.mjs:344,350`). The address half is what the
   `global_fetch_strictly_public` flag provides: fetch always goes out to the
   public internet, the same guarantee `workers-oauth-provider` relies on for
   its CIMD (`js:750-758` is a plain `fetch`, gated at `:4332`). Ship
   `workersCimdFetch` in `@lunora/auth`. It throws at construction when the
   flag is absent, accepts only https GET/HEAD, and otherwise calls `fetch`.
   On Node, point users at `@better-auth/cimd/node` (re-exported as
   `@lunora/auth/cimd/node` after review).
   _Rejected:_ keeping the "Workers cannot provide it" stance. It is stricter
   than the platform vendor's own implementation, and it leaves Lunora MCP
   servers unreachable by every CIMD-first client.
   _Rejected:_ a DNS-over-HTTPS resolve-then-check. Workers can't pin a
   connection to the resolved address, so it adds a TOCTOU window and no
   real guarantee.
4. **Step-up happens inside `createAuthedMcpFetchHandler`, through an opt-in
   `writeScope` option.** When it is set (e.g. `"lunora:write"`) and the
   claims lack that scope, the write tools **stay listed**, and a `tools/call`
   to one is answered with HTTP 403 `insufficient_scope scope="lunora:write"`.
   The handler peeks the method and tool name with `readScreenedBody` and
   throws a structural insufficient-scope error, which the better-auth gate
   turns into the challenge (`@better-auth/mcp` `index.mjs:81`). The
   challenge names every scope the operation needs in one go, as the spec asks.
   Without `writeScope`, today's hide-the-tools behaviour stays.
   _Rejected:_ replacing the hide behaviour outright. A client that cannot
   step up (a `client_credentials` agent) would then see tools it can never
   call. Also rejected: a JSON-RPC tool error instead of the HTTP 403. The
   spec puts the step-up signal on the HTTP challenge, and a tool error never
   reaches the client's auth layer.
5. **Well-known routing is a narrow, explicit widening of `isAuthRoutePath`.**
   `handleAuthRequest` also forwards `GET`/`HEAD` for the exact PRM paths of
   the configured `mcp({ resource })` and the path-inserted RFC 8414 path of
   the issuer. It derives them from the auth options at build time and never
   matches a `/.well-known/` prefix.
   _Rejected:_ telling users to add `httpAction`s for the well-knowns, which
   repeats the current docs gap in every app. Also rejected: moving the
   better-auth `basePath` to `/`, which steals the whole URL space.
6. **No better-auth family bump in this plan.** Add `@better-auth/cimd: 1.7.3`
   exactly, in lockstep with the family. The family bump to 1.7.7 is separate
   work and must re-read the `minimumFetchInterval` semantics change.
   _Rejected:_ bumping to 1.7.7 here, which mixes an unrelated lockstep upgrade
   (`@better-auth/expo` history in `pnpm-workspace.yaml:809-815`) into a
   compliance change.

## 5. Workstreams

**A. End-to-end gate test, then fix the documented wiring (S).**
Replace the gate double with a real `createAuth({ plugins: [jwt(), mcp(...)] })`
in a new `packages/mcp/__tests__/authed-http.e2e.test.ts`. `@lunora/auth` is a
devDependency only, which keeps the decision-2 rule about runtime deps. Mint a
token through the provider API, call the handler, and assert four things: a
401 challenge with `resource_metadata`, a 200 for a token whose audience is
`.../mcp`, a 401 for a token minted for another resource, and that the
scopes `mcp()` declares include `lunora:read` / `lunora:write`. Fix the
example in `authed-http.ts:17-37` and `docs/index.mdx` (`resource` passed to
`requireMcpAuth`, `scopes: ["lunora:read", "lunora:write"]` on `mcp()`) until
the test is green.

**Done.** `7e5e5a4c0` adds `packages/mcp/__tests__/authed-http.e2e.test.ts`
(11 tests) over a real `createAuth({ plugins: [jwt(), mcp()] })` on the memory
adapter. Tokens come from the provider's own token endpoint
(`client_credentials`, which issues the same audience-bound JWT without a
browser); `requireMcpAuth` verifies them against the instance's own JWKS.
`@lunora/auth` and `better-auth` are devDependencies of `@lunora/mcp` only.
`8ef83fa1d` fixes the example in `authed-http.ts` and `docs/index.mdx`.
Every suspected bug was **confirmed** against real better-auth 1.7.3:

- **Audience (bug 4a).** Without `resource`, `requireMcpAuth` refuses every
  correctly minted token with a 401 `invalid access token`, and its challenge
  names `/.well-known/oauth-protected-resource/api/auth`, a document nobody
  serves. First pinned by a regression test over better-auth's default; after
  review (`fd86333c9`) `@lunora/auth/plugins` ships its own `requireMcpAuth`
  that requires `resource` in the type and throws `AUTH_MCP_RESOURCE_INVALID`
  when it is missing or not an absolute URL, and the e2e test now checks that
  refusal instead (see §9 Q6).
- **Undeclared scope (bug 4b).** Without `scopes`, `mcp()` falls back to the
  OIDC defaults and refuses even to register a client for `lunora:read`
  (`invalid_scope`). Pinned by a test.
- **Discovery routing (bug 2).** `auth.handler` _does_ serve both
  `/.well-known/oauth-protected-resource/mcp` and the RFC 8414 path-inserted
  `/.well-known/oauth-authorization-server/api/auth` (the plugins' `onRequest`
  runs whatever the base path), but `handleAuthRequest` only forwards
  `/api/auth/*`, so both 404 through Lunora's routing. Shown with the
  conformance suite (§5 E). The docs now tell users to route the two exact paths
  to `auth.handler` themselves until B lands, derived with
  `mcpDiscoveryPaths(resource)` from `@lunora/auth/plugins` (added after review)
  rather than hard-coded.
- Negative tests added: foreign-audience token (401), forged signature (401),
  missing required scope (403 `insufficient_scope` naming `lunora:read`), and
  no unauthenticated request ever reaches the server factory.

**B. Route the discovery documents (M).**
Do decision 5 in `packages/auth/src/handler.ts` and `do-wiring.ts`, and in
the codegen emit if it hardcodes the default base path (`emit-app.ts:989`).
Re-export `oauthProviderAuthServerMetadata` only if routing cannot reach
`onRequest` for the path-inserted issuer path. Tests must fetch
`/.well-known/oauth-protected-resource/mcp` and
`/.well-known/oauth-authorization-server/api/auth` through the emitted worker
in D1 mode **and** DO mode, and assert that the metadata's `issuer` equals
the issuer used to build the URL (a client-side MUST). Golden fixtures for
apps without `mcp()` stay byte-identical.

**Stopped (§8 second STOP), not built.** The collision is real. The worker runs
`dispatchAuth` before everything else (`packages/runtime/src/create-worker.ts`,
`handle` → `dispatchAuth` → custom routes / `httpRouter`). So forwarding the
well-knowns from `handleAuthRequest` makes `@lunora/auth` win over an app's own
`httpAction` at the same exact path, and the interim docs recipe (A) tells users
to write exactly such a route. A second gap surfaced: in DO mode the worker never
sees the auth options (`createDoAuthWiring` only gets the namespace), so it
cannot derive the exact `mcp({ resource })` path without codegen passing it
through. Decisions needed:

1. **Precedence.** (a) Auth first, for the exact derived paths only, and only
   when an `oauth-provider`/`mcp` plugin is configured: simple, but it silently
   shadows a same-path `httpAction`. (b) App first: the runtime tries the auth
   well-knowns only after the app's routes miss. Nothing gets shadowed, but it
   needs a new fallback hook in `create-worker.ts`. (c) Auth first plus a
   codegen diagnostic when an `httpRouter` route matches a derived path.
   Recommendation: (b), because it changes nothing for an app that already
   routes these paths by hand.
2. **DO mode.** Pass the PRM path (from `mcp({ resource })`) and the issuer path
   from the auth declaration through codegen into `createDoAuthWiring`, or
   forward a fixed candidate set to the DO and fall through on its 404. The
   second costs a DO round-trip for every probe of those paths.

**Done, with the recommended answers ((b) app first; codegen passes the paths in
DO mode).** What shipped:

- **Runtime.** `WorkerOptions.authDiscoveryHandler` is the worker's _last_
  matcher: a `GET`/`HEAD` reaches it only after the explicit `routes`, the
  reserved `/_lunora/*` table and the `httpRouter` all missed. The router's own
  404 is what lets it through, so a route at the same path always wins, and a
  path the handler does not own keeps the router's 404 (body included). This
  replaces decision 5's "widen `isAuthRoutePath`": `handleAuthRequest` is
  unchanged.
- **Auth.** `authDiscoveryPaths(options)` derives the exact paths: the RFC 9728
  path for each `mcp({ resource })` and the RFC 8414 path for the issuer
  (`jwt.issuer`'s path when set, else the base path). It is empty unless an
  `oauth-provider` plugin (`mcp()` is one) is configured. better-auth keeps
  `mcp()`'s resource in a closure, so `@lunora/auth/plugins` now exports its own
  `mcp`, better-auth's with the resource recorded on the plugin under a
  `Symbol.for` key; an app using `@better-auth/mcp`'s `mcp` directly gets only
  the issuer path. `handleAuthDiscoveryRequest(auth, request)` serves them in D1
  mode, and `LunoraAuthDO.fetch` falls back to it after `/api/auth/*`.
- **DO mode.** `createDoAuthWiring({ discoveryPaths })` returns a
  `discoveryHandler` that forwards only those paths; codegen derives them in the
  worker with `authDiscoveryPaths(authDeclaration.options(env))`. Any other probe
  never reaches the object.
- **Base path.** `emit-app.ts` still calls `handleAuthRequest(auth, request)`
  with the default `/api/auth`, and DO mode fixes it too, as before. The
  discovery derivation reads `basePath` from the options, so the
  authorization-server path always matches the issuer better-auth reports.
  Making the routed base path configurable is a separate change.
- `oauthProviderAuthServerMetadata` is **not** re-exported: `auth.handler`'s
  `onRequest` answers the path-inserted issuer path.
- Tests: `packages/auth/__tests__/discovery.behaviour.test.ts` (10) fetches both
  documents through a real `createWorker` wired the way codegen wires it, in D1

## 8. Risks & STOP conditions

- **STOP** if better-auth's insufficient-scope check (`isInsufficientScopeError`)
  is a class or brand check that a structurally typed error can't satisfy.
  Do not add a better-auth dependency to `@lunora/mcp` to get past it. Have
  `protect` accept an optional `challenge(scopes)` callback instead, and
  bring that design back before building it.
- **STOP** if routing well-knowns from `handleAuthRequest` collides with an
  app's own `/.well-known/*` `httpAction` in the codegen dispatch order. Raise
  the precedence question with the user rather than choosing silently.
- **Risk:** `global_fetch_strictly_public` is a weaker guarantee than the
  letter of cimd's transport contract (no DNS pinning). Mitigation: document
  it, and make `isMetadataDocumentUrlAllowed` an origin allowlist the
  recommended production setting. It's the same trade Cloudflare's package
  makes.
- **Risk:** cimd's metadata cache is an in-memory LRU per plugin instance
  (`index.d.mts:107-113`). On Workers every isolate refetches, and the
  rate-limit budgets are per isolate too. Mitigation: accept it for now. A
  shared cache needs the `caches` API, which is a follow-up and not a
  blocker.
- **Risk:** the confirmation digest is shared across principals
  (`write-confirmation.ts:36-43`), and step-up makes multi-principal write
  servers more likely. Out of scope here. Note it in the step-up docs.
- **Perf watch:** CIMD adds an outbound fetch on the first `/authorize` per
  client per isolate. That's authorization-path latency, not MCP-request
  latency, and there's no `__bench__` suite for auth. Log the fetch duration
  through `onError` / the hooks instead.
